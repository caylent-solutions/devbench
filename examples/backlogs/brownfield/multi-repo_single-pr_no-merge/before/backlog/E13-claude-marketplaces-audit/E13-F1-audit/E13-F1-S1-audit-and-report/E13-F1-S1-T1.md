# E13-F1-S1-T1: Audit kanon-claude-marketplaces against spec standards; commit follow-up-issue report

## Status: in-queue

## Target Repository

- **Repo:** `caylent/kanon-claude-marketplaces`

## Description

Run the four kanon audit / validate commands shipped by E5 against the
checked-out `caylent/kanon-claude-marketplaces` working tree, classify
every finding by severity, and author a comprehensive Markdown audit
report committed to the target repo at
`audit-reports/2026-05-kanon-deps-spec-audit.md`.

The audit is **read-only against the target repo source tree.** The
only file this Task writes inside the target repo is the audit report
file in the Changes Manifest below. The Task does NOT modify, rename,
or delete any other repo content; it does NOT auto-fix any finding.
Remediation lives in the follow-up issues the operator files after
this Task lands.

### What "the four commands" means

Per the spec, the audit runs all four of the following against the
target repo's working tree (each command's stdout / stderr is captured
verbatim and embedded in the report):

1. `kanon catalog audit <repo-path> --check all --format json`
2. `kanon validate xml <repo-path>`
3. `kanon validate marketplace <repo-path>`
4. `kanon validate metadata <repo-path>`

Per soft-spot rule 4 (spec Section 3.5), `kanon catalog audit` also
re-runs the `<remote>`-resolution walk that `kanon validate
marketplace` performs, so the four commands collectively cover every
soft-spot 1-5 rule plus the trust-model rules from spec Section 3.6.

### Target-repo shape (what to expect)

The target repo's layout differs from `caylent-private-kanon`:

- No `repo-specs/` directory.
- No `*-marketplace.xml` files anywhere in the tree.
- Plugin content lives under `common/` with each plugin's
  `.claude-plugin/marketplace.json` describing it.
- A top-level `repo-config.json` declares the monorepo's
  `marketplace_root`, `reserved_directories`, and
  `flattening_strip_prefixes`.

Because the repo has no XML manifests, several kanon commands have
nothing to validate. The audit MUST report this state as an INFO
finding rather than treating "zero inputs found" as a silent pass; the
report records the audit-coverage gap so the follow-up issues
explicitly acknowledge whether kanon's existing standards are
applicable to this repo's `.claude-plugin/marketplace.json` shape OR
whether new kanon validators are needed (the latter is itself a
follow-up issue).

### Report contents

The audit report's body covers:

1. **Provenance header.** First line of the report body reads:
   `Generated by E13-F1-S1-T1 against kanon-claude-marketplaces commit <SHA>`
   where `<SHA>` is the output of `git rev-parse HEAD` run inside the
   target repo at audit time. Includes the audit run timestamp in ISO
   8601 UTC and the kanon CLI version reported by `kanon --version`.
2. **Back-link** to spec Section 9c (`spec/kanon-list-add-lock-features-spec.md`
   (ref)) and to spec Section 3.5 and Section 3.6.
3. **Command outputs.** Verbatim stdout + stderr + exit code from each
   of the four commands listed above. Each block is preceded by the
   exact command line used so the audit is reproducible.
4. **Findings by soft-spot rule.** A section per soft-spot rule from
   spec Section 3.5 (rules 1 through 5) plus a section for spec
   Section 3.6 trust-model violations. Under each rule, every distinct
   finding is listed once with: finding code (the code emitted by the
   kanon CLI, e.g. `MISSING_REQUIRED_FIELD`), severity
   (`ERROR` / `WARN` / `INFO`), the offending path(s) inside the
   target repo, and the kanon-CLI-supplied remediation text.
5. **Recommended follow-up issues.** For each `ERROR` or `WARN`
   finding, a ready-to-paste GitHub-issue body containing: title,
   labels (`kanon-deps-spec`, severity label), problem summary,
   affected paths, remediation steps copied from the kanon CLI
   output, and a reference back to the spec rule the violation
   pertains to. `INFO` findings are documented but do not get
   issue-body drafts (per AC-FUNC-003 below).
6. **Operator filing instructions.** A short section telling the
   operator how to file each issue via the kanon-claude-marketplaces
   GitHub issue tracker (UI link, copy-paste flow). The instructions
   explicitly note that the audit task does NOT file issues itself
   (provider-agnostic constraint per spec Section 3.6).
7. **Summary table.** Count of findings by severity and by soft-spot
   rule, plus an overall pass / fail indication (FAIL when any ERROR
   finding exists, WARN when only WARN/INFO findings exist, PASS when
   only INFO findings exist).

### Approach

1. **Establish provenance.** `cd` into the target repo working tree;
   capture `git rev-parse HEAD`, current ISO 8601 UTC timestamp, and
   `kanon --version`. Stash these for the report header.
2. **Run the four commands.** For each of `kanon catalog audit
   <repo-path> --check all --format json`, `kanon validate xml
   <repo-path>`, `kanon validate marketplace <repo-path>`, and `kanon
   validate metadata <repo-path>`: capture stdout, stderr, and the
   exit code. Do NOT abort on a non-zero exit; the report must include
   every command's output even when one fails (a non-zero exit is
   itself a finding the report documents).
3. **Parse the findings.** For `kanon catalog audit --format json`
   parse the structured `findings` array directly. For the three
   `kanon validate *` commands parse stderr line-by-line against the
   `ERROR:` / `WARN:` / `INFO:` prefixed lines defined by the spec
   error-message shape (spec Section 4).
4. **Map findings to soft-spot rules.** Each finding-code emitted by
   `kanon catalog audit` maps directly to one of soft-spot rules 1-5.
   `kanon validate xml` findings map to schema correctness (no soft-spot
   bucket; surfaced as a separate section in the report). `kanon
   validate marketplace` findings map to soft-spot 4. `kanon validate
   metadata` findings map to soft-spot 1, 2, or 3 depending on the
   finding code. Findings whose mapping is ambiguous are placed in a
   dedicated "uncategorized" section in the report with a TODO note
   asking the operator to clarify; the report does NOT silently drop
   any finding.
5. **Draft follow-up issue bodies.** For each ERROR or WARN finding,
   compose an issue-body block per the report-contents spec above.
   Group issues by soft-spot rule so the operator can file a batch per
   rule if preferred.
6. **Write the report file.** Author the Markdown report under the
   target repo at the path in the Changes Manifest. The file is the
   only target-repo change this Task makes.
7. **Verify reproducibility.** Re-run the audit a second time against
   the same target-repo HEAD; confirm the second run's findings list
   matches the first run's exactly (every command must be
   deterministic against a fixed input tree). The TDD Cycle Log
   captures both runs' exit codes.
8. **Stage only the Manifest file.** `git add` the single report file
   listed in the Changes Manifest; nothing else.

### Code Standards

All code in this work unit MUST comply with the following rules. These are checked by the LLM review judges (`code_review`, `test_review`, `doc_review`, `changes_manifest`, `security_review`) and trigger `REVIEW_FAIL` when violated. The work unit cannot reach `done` until every judge logs `REVIEW_PASS`.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.

#### Architecture Principles

- **SOLID** -- Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
- **DRY** -- Extract shared logic into reusable helpers under `src/kanon_cli/utils/`, `src/kanon_cli/core/`, or `src/kanon_cli/commands/` as appropriate. No duplicate code.
- **12-Factor App** -- Config from environment or YAML. Explicit dependencies declared in `pyproject.toml`. Logs to stdout/stderr.

#### Testing Rules

- **TDD MANDATORY** -- Write failing tests BEFORE implementation. Source/test atomicity (`devbench/docs/source-test-atomicity.md`): every new `.py` source file under `src/kanon_cli/` has its matching `tests/unit/test_<basename>.py` in the SAME work unit's Changes Manifest.
- **NO STUB TESTS** -- Every test must have assertions that can actually fail. No `assert True`, no `assert obj is not None` as the only assertion, no TODO-marked test bodies.
- **TEST ERROR PATHS** -- Every error condition must have a test. Network failures, malformed inputs, missing files, permission errors, timeouts, signal interruption.
- **PARAMETRIZE** -- Use `@pytest.mark.parametrize` for multiple scenarios. One test function per logical assertion.
- **REAL TESTS ONLY** -- Integration tests run against a real fixture git server (or mocks matching `git ls-remote --refs` output verbatim). No `MagicMock` over network APIs without a real-server parity test.
- **NO SKIPS / XFAILS / XPASSED** -- AC-FINAL-013. Skipped tests hide regressions.

#### Git Rules

- **STAGE ONLY** -- Use `git add` for relevant files (only those in this work unit's `## Changes Manifest`). Do NOT commit, push, or create PRs from inside the executor. The orchestrator owns the git-ops lifecycle.
- **NO --no-verify** -- Never bypass git hooks.
- **SELECTIVE STAGING** -- Only stage files in the Changes Manifest. `git add -A` is forbidden; use explicit `git add <path>` per file.

#### Security Rules

- **NO SECRETS** -- No API keys, tokens, passwords, GitHub PATs, or SSH keys in source code, tests, or fixtures.
- **NO eval() / exec()** -- Never execute dynamic code from external input.
- **NO PROVIDER-SPECIFIC API CALLS** -- Per spec Section 3.6, kanon NEVER calls provider HTTP APIs (`api.github.com`, `gitlab.com/api`, etc.) and NEVER shells out to provider CLIs (`gh`, `glab`, `bb`, `tea`, `aws codecommit`, `az repos`). Every git interaction is via the `git` binary only. This Task inherits the constraint: it does NOT file GitHub issues itself; the report instead documents the issue bodies for the operator to file manually.
- **NO AUTH HANDLING** -- kanon NEVER prompts for credentials, NEVER caches them, NEVER reads them from anywhere except by delegating to the operator's git client. Auth-error patterns are detected in stderr for retry-policy purposes only (`GIT_AUTH_ERROR_PATTERNS` in `constants.py`).

#### Error Handling Contract

- Raise specific exceptions (not generic `Exception`).
- Include context in error messages: file paths, variable names, expected vs actual values, the operator's likely next step.
- Never catch and discard exceptions.
- Never call `sys.exit()` from library code; only from CLI command handlers in `src/kanon_cli/commands/` or `src/kanon_cli/cli.py`.
- Error messages follow the standard shape per spec Section 4: `ERROR: <one-line summary>` then optional context lines (wrapped at 80 cols), then a remediation line when applicable.
