# E11-F4: Migrate the `security-code-review` catalog entry

## Status: in-queue

## Description

Bring the `security-code-review` catalog entry into Section 3.5 soft-spot
compliance. The entry's manifest XML lives at
`repo-specs/common/security-and-compliance/code-review/full-review-marketplace.xml`
and the legacy author-facing README lives at
`catalog/security-code-review/kanon-readme.md` (note the `kanon-readme.md`
filename, not `README.md`).

**Entry-name resolution.** The XML filename uses `full-review-` as a
prefix but the legacy catalog directory is named `security-code-review/`.
The two plausible entry-names are `full-review` (matches XML filename)
and `security-code-review` (matches the catalog directory). We choose
`security-code-review`: it is more descriptive of the entry's purpose,
matches the catalog-directory convention used elsewhere in the repo,
and aligns with the `<display-name>` already set to `"Security Code
Review"`. The rename rationale is documented in the entry's
`<description>` when migrated.

Today's `<catalog-metadata>` block carries `display-name="Security Code
Review"`, `type`, `description`, `owner-name`, `owner-email`, `keywords`,
and `version` as attributes but is MISSING the REQUIRED `<name>` element.
The single referenced `<project>` revision pins
`refs/tags/security-and-compliance/code-review/>=0.1.0,<1.0.0` against
the inherited `caylent` remote (resolved via
`repo-specs/git-connection/remote.xml`); the PEP 440 last-path-component
of that constraint is `>=0.1.0,<1.0.0`, which IS PEP 440 compliant.

This feature decomposes into a single story (`E11-F4-S1`) with a single
task (`E11-F4-S1-T1`).

Spec source: spec Section 9b Phase 1; Section 3.5 soft-spot rules 1-5.
