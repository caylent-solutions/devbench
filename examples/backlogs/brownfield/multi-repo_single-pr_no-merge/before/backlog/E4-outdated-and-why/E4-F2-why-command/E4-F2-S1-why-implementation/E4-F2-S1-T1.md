## Description

Implement the core `kanon why` command as a new module `src/kanon_cli/commands/why.py`. The command:

1. **Reads `.kanon`** at `--kanon-file` (default `KANON_KANON_FILE` = `./.kanon`).
2. **Resolves the full dependency tree**:
   - If `.kanon.lock` exists at `--lock-file` (default derived from `--kanon-file`), the tree is
     read directly from the lockfile -- every node already has its resolved SHA. This is the
     reproducible path; no network calls needed.
   - Otherwise, live-resolve the tree against the catalog (which requires a catalog source via
     `--catalog-source` or `KANON_CATALOG_SOURCE`). Live-resolution uses the existing tree-walker
     from `kanon install`'s resolution stage (every `KANON_SOURCE_*` block -> `<catalog-metadata>`
     entry -> `<include>` / `<project>` graph). Each node carries `{kind, name, ref, sha, url}`.
3. **Locates the requested node**: T1 implements ONLY the URL-match category (spec Section 4.5
   step 2 item (a)): canonicalize the argument via `core/url.py::canonicalize_repo_url` and look
   for a `<project>` node whose canonicalized URL equals the canonicalized argument. (XML-path
   matching and source-name matching arrive in E4-F2-S1-T2 alongside ambiguity detection;
   closest-match suggestions arrive in T3; JSON output in T4.)
4. **Walks every chain ending at the requested node** and prints one line per chain to stdout:

   ```
   <top-level-source> -> <xml-manifest-path>@<resolved-sha> -> ... -> <project>@<resolved-sha>
   ```

   The walker is DFS-based: for each top-level `KANON_SOURCE_*` source, perform a depth-first
   traversal of the resolved tree, collecting ancestor paths that reach the requested project URL.
   Each ancestor path becomes one printed chain.
5. **Default format** is `text` (controlled by `KANON_WHY_FORMAT`). The `--format` argparse flag
   has `choices=("text",)` for this task; T4 extends to `("text", "json")`.

This task scopes ONLY to:

- URL-match-by-canonicalized-equality (the most common and least ambiguous case);
- chain-walking and text printing;
- subcommand registration in `cli.py`;
- the `KANON_WHY_FORMAT = "text"` constant.

Not-found in T1 is a hard error with the standard `ERROR: <name-or-url> not found in resolved
tree` message. The closest-match Levenshtein suggestion lands in T3. Ambiguity errors land in T2.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.5 behaviour steps 1, 2 (item a),
4 (text format). Section 7 for `KANON_WHY_FORMAT` env-var.

### Approach

   chain tree (one top-level source -> one `<project>` matching the argument URL) prints exactly
   one line; (b) multi-chain tree (one project reachable via two different `<include>` paths from

2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
