# E1-F1-S1-T2: Loud-error in `_resolve_constraint_from_tags` when zero PEP 440 tags remain

## Status: in-queue

## Target Repository

- **Repo:** `caylent-solutions/kanon`
- **Branch:** `backlog/e1-f1-s1-t2`

## Description

Make `_resolve_constraint_from_tags` in `src/kanon_cli/version.py` loudly
report which non-PEP-440 tag names it skipped when zero PEP 440-parseable
versions remain under the requested prefix. Today's narrow message at
line 209 reads only:

```
No parseable version tags found under '<prefix>'
```

After this task, when the function would raise that error, the message
MUST also enumerate the non-PEP-440 tag names that were skipped (capped
at the first 10, sorted deterministically for stable test output), plus
a remediation pointer at `kanon catalog audit --check tag-format`. The
new shape:

```
ERROR: No PEP 440-parseable version tags found under '<prefix>'.
Skipped <N> tag(s) whose last path component is not a valid PEP 440 version:
  - <tag_name_1>
  - <tag_name_2>
  ... (showing first 10 of <N>)
Run 'kanon catalog audit --check tag-format' against the manifest repo
to identify every non-PEP-440 tag, then ask the catalog author to rename
them to PEP 440 form (e.g., 'v1.0.0' -> '1.0.0').
```

When the prefix filter matches zero tags AT ALL (not "matches but none
are PEP 440"; literally zero candidates), today's behaviour is preserved
verbatim (a clear "no tags under prefix" message). The new loud-listing
applies only to the "filtered candidates exist but none parse" path.

The function signature and return type are unchanged. The exception
class raised is the same (`ValueError`); only the message text changes.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 0.4
(PEP 440 enforcement on tag names -- consumer-side loud error) and
Section 13 decision 14.

### Approach

   cases that build a synthetic `tags` list containing a mix of
   PEP 440-parseable and non-PEP-440 tag names, set the prefix so only
   non-PEP-440 candidates remain, and assert that the raised `ValueError`
   message:
   - Starts with `"ERROR: No PEP 440-parseable version tags found under '<prefix>'."`.
   - Contains a `"Skipped <N> tag(s) whose last path component is not a valid PEP 440 version:"` line.
   - Lists the first 10 skipped tag names (deterministically sorted), one per `  - ` indented bullet.
   - When more than 10 skipped tags exist, ends the bullet list with `"... (showing first 10 of <N>)"`.
   - Concludes with the remediation pointer referencing `kanon catalog audit --check tag-format`.
   Run `uv run pytest tests/unit/test_version.py -v`; verify cases FAIL.
2. **TDD RED (control case):** Add a parametrized case where the prefix
   filter matches zero tags AT ALL; assert the message is byte-for-byte
   today's `"No parseable version tags found under '<prefix>'"` so the
   non-loud path is preserved. Run; confirm the existing-behaviour case
   PASSES already (regression guard).
3. **TDD GREEN:** Modify `_resolve_constraint_from_tags` in
   `src/kanon_cli/version.py` so that:
   - Before today's "no parseable tags" raise, collect the list of
     filtered-candidate tag names that failed `packaging.version.Version`
     parsing (call this `skipped`).
   - If `skipped` is empty (no candidates under prefix at all), raise
     the existing narrow message verbatim.
   - If `skipped` is non-empty, build the new multi-line message per
     the format above (deterministic sort of `skipped`, cap at 10,
     suffix with `(showing first 10 of <N>)` only when `N > 10`).
   - Raise the same `ValueError` class with the new message.
4. **TDD REFACTOR:** Extract the message-formatting into a small private
   helper (e.g., `_format_zero_pep440_tags_error(prefix, skipped)`)
   inside the same module so the resolver function stays focused and
   the formatting is unit-testable in isolation (SRP, DRY).
5. **Integration:** Extend the integration test built in T1
   (`tests/integration/test_version_widened_bare_pep440.py`) with a new
   case: build a fixture git repo whose tag set is entirely non-PEP-440
   (`v1.0.0`, `v1.1.0`, `release-2024`) and call `resolve_version` with
   a `==1.0.0`-style constraint; assert the raised `ValueError` matches
   the new format and lists the three tag names. Document the new case
   in the test file's module docstring.
6. **Docs:** Update `docs/version-resolution.md` to show the new
   loud-error message verbatim and the remediation pointer. Update the
   docstring on `_resolve_constraint_from_tags` to reference the new
   message contract.

   `uv run pytest tests/ -v && uv run ruff check src tests && uv run ruff format --check src tests && uv run mypy src && uv run bandit -r src -ll`.
