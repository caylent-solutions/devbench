# E3-F2: `kanon_hash()` deterministic SHA-256 over `.kanon`

## Status: in-queue

## Description

Introduces `kanon_hash(kanon_path) -> str`, a deterministic SHA-256 over the
normalised form of a `.kanon` file. The hash is the semantic consistency
check `kanon install` and `kanon doctor` use to detect that the operator has
edited `.kanon` since the last successful install; mismatch triggers the
"hash mismatch" branch of the install state machine (E3-F3) which directs
the operator to run `--refresh-lock` or `--refresh-lock-source`.

Algorithm (spec Section 5.1):

1. Parse the `.kanon` file via the existing `parse_kanonenv`.
2. Extract every `KANON_SOURCE_<name>_{URL,REVISION,PATH}` triple. Discard
   comments, blank lines, and any non-`KANON_SOURCE_*` keys (specifically
   `GITBASE`, `CLAUDE_MARKETPLACES_DIR`, and `KANON_MARKETPLACE_INSTALL`,
   which are workspace-environment values rather than consumer state).
3. Sort triples by source name; within a source, `URL` precedes `REVISION`
   precedes `PATH`.
4. Serialise as `name\turl\trevision\tpath\n` per source. Reject any value
   containing literal tab, NUL, or newline at serialisation time (hard
   error with a clear remediation pointer).
5. SHA-256 the serialised bytes; return the hex digest prefixed with
   `sha256:`.

Required properties (each one is a parameterised test in T1):

- Re-ordering source blocks in `.kanon` does NOT change the hash.
- Adding or modifying comments does NOT change the hash.
- Changing any `REVISION` value DOES change the hash.
- Changing a source name DOES change the hash.
- Changing `GITBASE`, `CLAUDE_MARKETPLACES_DIR`, or
  `KANON_MARKETPLACE_INSTALL` does NOT change the hash.

This feature has no upstream dependencies on E1 or E2; it depends only on
the existing `parse_kanonenv` primitive that ships in today's kanon
codebase.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 5.1.
