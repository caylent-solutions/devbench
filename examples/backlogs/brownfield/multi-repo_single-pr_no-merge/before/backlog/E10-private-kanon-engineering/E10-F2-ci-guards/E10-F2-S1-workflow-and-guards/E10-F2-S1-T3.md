# E10-F2-S1-T3: CI guard pep440-tags.yml -- validate tag names against PEP 440

## Status: in-queue

## Description

Create the GitHub Actions workflow `.github/workflows/pep440-tags.yml`
in the `caylent/caylent-private-kanon` repo. The workflow validates that
any tag pushed to the repo, or any tag referenced by a PR, has a
last-path-component that is a valid PEP 440 version per spec Section
3.5 soft-spot 5 and Section 9a CI bullet 5.

### Behaviour envelope (deprecation window)

Per spec Section 9a bullet 5 and Section 15 (future work):

> Warning-only initially. Future release promotes to hard error after a
> deprecation window.

The initial implementation emits a WARN-shape annotation (`::warning::`)
on every non-PEP-440 tag but exits zero so the build does not fail. A
comment in the workflow file documents the planned promotion path:
flipping the `STRICT_MODE` env var (or a one-line `exit 1` toggle) to
hard-error once the deprecation window closes. The promotion is NOT
gated on E12 completion; it is gated on the spec-Section-15 follow-up.

### Implementation

1. Triggers:
   - `on: push: tags: ['**']` for direct tag pushes.
   - `on: pull_request: {}` so PRs that propose a tag (e.g., a
     release-prep PR that touches `CHANGELOG.md` and a new tag in a
     refs file) are scanned for any tag-like reference. For PRs the
     job inspects the set of tags reachable from the PR head that are
     NOT reachable from the base; this catches any tag introduced as
     part of the PR.
2. Job `pep440-tags` on `ubuntu-latest`:
   - `actions/checkout@<pinned>` with `fetch-depth: 0` and
     `fetch-tags: true` so every tag is available.
   - Install Python and the `packaging` library:
     `python -m pip install packaging==<pinned-version>` (the pinned
     version lives in the workflow `env:` block, e.g.,
     `PACKAGING_VERSION: '<pin>'`, so an operator update does not
     require editing the `run:` shell code).
   - Enumerate candidate tags:
     - For `push: tags`: `${{ github.ref_name }}` (a single tag).
     - For `pull_request`: `git tag --contains ${{
       github.event.pull_request.head.sha }} --no-contains ${{
       github.event.pull_request.base.sha }}` (the set of tags
       reachable from the PR head but not from the base).
   - For each candidate tag, take the last path component (everything
     after the final `/`) and validate it via:
     ```bash
     python -c "import sys; from packaging.version import Version; \
       Version(sys.argv[1])" "${last_component}"
     ```
     A non-zero exit from `python -c` means the component is not a
     valid PEP 440 version.
   - For every invalid component, emit `::warning file=...,title=Tag
     not PEP 440::<tag> last-component '<last>' is not a valid PEP
     440 version` to the GitHub annotations stream so the warning
     surfaces in the PR UI.
   - Exit code: zero in the initial implementation regardless of how
     many warnings were emitted. A clearly-commented `STRICT_MODE`
     env var (default `false`) gates a future `exit 1` when any
     invalid tag was seen. The promotion is the operator's
     one-character change at follow-up time.

### Workflow shape

- `name: pep440-tags`
- `on:`
  - `push: { tags: ['**'] }`
  - `pull_request: {}`
- `jobs:` one job (`pep440-tags`); `shell: bash`; `set -euo pipefail`;
  pinned action versions; `packaging` library pinned via workflow
  `env:`.
- Every configurable value (the pinned `packaging` version, the
  `STRICT_MODE` toggle, the annotation title text) lives in the
  workflow `env:` block.

### Approach

1. **Confirm the PEP 440 validation primitive matches E5-F2-S1-T6.**
   E5-F2-S1-T6 implements the catalog-side PEP 440 check using
   `packaging.version.Version`. This workflow uses the same library
   so the rule is consistent across CLI and CI. The workflow's
   `python -c "from packaging.version import Version; Version(...)"`
   call mirrors the CLI's implementation.
2. **Survey existing workflows.** `ls .github/workflows/` to confirm
   `pep440-tags.yml` does not already exist.
3. **Author the workflow file.** Use the canonical `name`, `on`,
   `env`, `jobs` skeleton; one job; pinned action versions; pinned
   `packaging` version via `env`; `shell: bash`; `set -euo pipefail`.
4. **Test the push-trigger path.** Push a tag with a valid PEP 440
   last-component (e.g., `1.0.0`); confirm the workflow runs and
   exits zero with no warnings. Push a tag with a non-PEP-440
   last-component (e.g., `v1.0.0` or `release-2024`); confirm the
   workflow runs, emits a `::warning::` annotation, and still exits
   zero (deprecation-window behaviour).
5. **Test the PR-trigger path.** Open a fixture PR whose head
   contains a new tag (`refs/tags/v2.0.0`); confirm the workflow
   detects the tag via `git tag --contains <head> --no-contains
   <base>` and emits the warning.
6. **Verify STRICT_MODE toggle.** Manually flip the `STRICT_MODE` env
   to `true` against the same fixture; confirm the workflow now
   exits non-zero on the same input. Revert.
7. **Stage selectively.** `git add .github/workflows/pep440-tags.yml`
   only.

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. 2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only.
