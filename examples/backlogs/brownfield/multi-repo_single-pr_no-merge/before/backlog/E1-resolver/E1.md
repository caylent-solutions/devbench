# E1: Resolver semantics, URL canonicalization, @ splitter coverage, and shared CLI args

## Status: in-queue

## Description

Foundation epic for the kanon dependency-manager features release. Ships the
resolver-level changes that every later command depends on:

- **Widen bare PEP 440 detection** in `version.py::_normalize_bare_semver_to_tag`
  so `kanon add foo@1.0.0a1` and `kanon add foo@1.0.0+local` resolve to
  `refs/tags/<spec>` (today's narrow regex `^\d+(?:\.\d+){1,2}$` only matches
  `\d.\d.\d`).
- **Make non-PEP-440 tag resolution loud** in `version.py::_resolve_constraint_from_tags`:
  when zero PEP 440-parseable tags remain under the prefix, raise a structured
  error naming the skipped tag names instead of the current generic
  `"No parseable version tags found under '<prefix>'"`.
- **Add `core/url.py::canonicalize_repo_url`** -- new helper used by conflict
  detection (Section 4.7), `kanon why` URL matching (Section 4.5), and the
  lockfile (Section 5). Normalises scheme equivalents (ssh / https / git@),
  strips `.git` suffix, trailing slashes, embedded user-info; rejects URLs
  with query strings or fragments.
- **Harden the `@`-splitter test coverage** in `_parse_catalog_source` for
  SSH-URL-with-`@`-in-user-info cases (`git@host:org/repo.git@main`).
- **Move the `--catalog-source` flag definition** from `commands/bootstrap.py`
  to a new shared module `core/cli_args.py` so the canonical definition is
  not coupled to the deprecating bootstrap shim (E6 depends on this).

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.0 (Resolver
semantics) and Section 3 (Existing primitives).

E1 is the foundation: E2 (list/add/remove), E3 (lockfile + install extension),
E4 (outdated/why), and E5 (doctor + catalog audit) all import from the
modules E1 introduces or modifies. Without E1 landing first, none of the new
commands can resolve `@<spec>` tokens or normalise URLs.
