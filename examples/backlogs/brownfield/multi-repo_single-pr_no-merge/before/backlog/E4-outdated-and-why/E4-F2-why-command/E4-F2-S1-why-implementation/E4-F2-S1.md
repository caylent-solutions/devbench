# E4-F2-S1: `kanon why` implementation

## Status: in-queue

## Description

Implement the `kanon why` command in four sequential tasks that share the same source file
(`src/kanon_cli/commands/why.py`) and the same test fixture structure under
`tests/unit/test_why*.py` + `tests/integration/test_why*.py`.

- **T1** lands the core chain-walker (subcommand registration, `.kanon` read, full-tree resolution
  via lockfile or live-resolve, per-chain text printing, default `text` format via
  `KANON_WHY_FORMAT`, URL-match category).
- **T2** adds the three-category precedence resolver and the ambiguity hard error.
- **T3** adds the Levenshtein closest-match suggestion on not-found.
- **T4** adds the `--format json` output path.

T1 ships the command file end-to-end with URL matching only; T2/T3/T4 each amend `why.py` to add
their respective behaviour. Each task pairs its source change with a dedicated
`tests/unit/test_why_<feature>.py` and a matching `tests/integration/test_why_<feature>.py` so
source/test atomicity is preserved (see `devbench/docs/source-test-atomicity.md`).

T3 introduces a small Levenshtein-distance helper. To keep the helper reusable and unit-testable in
isolation (and because the spec calls it out as a generic edit-distance helper), it lands in
`src/kanon_cli/utils/levenshtein.py` with its matching `tests/unit/test_levenshtein.py`.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.5 steps 1-5 and Section 7
(`KANON_WHY_FORMAT`, `--format`).
