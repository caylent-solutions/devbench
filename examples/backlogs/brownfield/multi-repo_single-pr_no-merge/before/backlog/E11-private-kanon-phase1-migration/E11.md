# E11: caylent-private-kanon Phase 1 -- per-entry `<catalog-metadata>` migration

## Status: in-queue

## Description

This epic executes Phase 1 of the operational migration described in spec
Section 9b: bring every catalog entry in the `caylent/caylent-private-kanon`
repo into 100% compliance with the soft-spot rules codified in spec
Section 3.5 (REQUIRED `<catalog-metadata>` fields, source-name derivation,
entry-name uniqueness, remote-url discoverability, PEP 440 tag-format).
The legacy nested `catalog/<name>/` directory tree is NOT deleted in this
epic -- that is Phase 2 (E12), which is gated on every Phase-1 task being
done. This epic only migrates author-facing metadata out of the legacy
per-entry directories and into each manifest's `<catalog-metadata>` block.

The repo today has five catalog entries (one `*-marketplace.xml` per entry,
nested under `repo-specs/common/<topic>/<sub>/`):

| Feature | Entry-name | Marketplace XML (repo-relative) | Legacy README (repo-relative) |
|---|---|---|---|
| E11-F1 | `devbench-backlog-builder` | `repo-specs/common/software-development/requirements/devbench-backlog-builder/devbench-backlog-builder-marketplace.xml` | `catalog/devbench-backlog-builder/README.md` |
| E11-F2 | `history` | `repo-specs/common/claude-tools/history/claude-history-marketplace.xml` | `catalog/history/README.md` |
| E11-F3 | `immutable-audit-trail` | `repo-specs/common/sdlc/general/pr-ready/immutable-audit-trail/immutable-audit-trail-marketplace.xml` | `catalog/immutable-audit-trail/README.md` |
| E11-F4 | `security-code-review` | `repo-specs/common/security-and-compliance/code-review/full-review-marketplace.xml` | `catalog/security-code-review/kanon-readme.md` |
| E11-F5 | `builders-plugins` | `repo-specs/common/builders/builders-plugins/builders-plugins-marketplace.xml` | (none -- no legacy catalog dir) |

The `kanon` self-bootstrap entry (`catalog/kanon/`) is intentionally
out-of-scope for E11; it is handled by E6 (bootstrap deprecation), which
deletes the bundled catalog tree shipped inside the kanon wheel.

Per-entry scope (homogeneous across F1..F5):

1. Open the entry's `*-marketplace.xml`.
2. Audit the `<catalog-metadata>` block. Add any missing REQUIRED fields
   (`name`, `display-name`, `description`, `version`) per soft-spot 1.
   Note: every entry today carries `display-name`, `description`, and
   `version` as attributes but is MISSING the REQUIRED `<name>` element
   (or `name` attribute) that pins the entry-name; this is the primary
   migration delta.
3. Migrate the legacy `catalog/<name>/README.md` (or `kanon-readme.md`)
   content into `<catalog-metadata><description>` **verbatim** -- preserve
   the full file content. Truncation / human-review trim decisions
   happen at PR time, not inside the autonomous loop.
4. Verify the chosen entry-name is unique across the whole repo (soft-spot
   3). When an XML filename does not match the catalog directory name
   (E11-F2 `claude-history-marketplace.xml` vs `catalog/history/`;
   E11-F4 `full-review-marketplace.xml` vs `catalog/security-code-review/`)
   pick the catalog-dir name as the entry-name and document the rename
   in the `<description>`.
5. Verify every `<project remote="X">` URL is reachable via the
   `<include>` chain (soft-spot 4) by running
   `kanon catalog audit --check remote-url <this-XML>` and confirming
   exit 0.
6. Verify referenced `<project>` revisions are PEP 440-compliant tags
   (soft-spot 5). If any are not, file an issue against the upstream
   repo and document the issue link + non-compliant tag(s) in the
   `<description>`.
7. Acceptance per task: `kanon catalog audit --check all <this-XML>`
   exits 0 (with PEP 440 tag-format warnings tolerated unless `--strict`
   per E10-F2 CI policy).

Tasks across F1..F5 are parallel-safe: each touches a different XML and
(at most) a different legacy README, with no overlapping files. The
autonomous loop runs all five tasks concurrently. Every Phase-1 task
blocks the single Phase-2 task in E12 (which deletes `catalog/` in its
entirety).

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 9b
Phase 1; Section 3.5 soft-spot rules 1-5; Section 4.8 (`kanon catalog
audit`).

Upstream dependencies:

- E10 -- caylent-private-kanon engineering + CI (the CI guards must be
  green before per-entry migrations land, so regressions are caught at
  PR time).
- E5-F2 -- `kanon catalog audit` implementation in the kanon CLI
  (required to run the acceptance command per task).
