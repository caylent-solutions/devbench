# E7-F2-S1: Six dynamic completers + mid-token splitter

## Status: in-queue

## Description

Story scope: ship every dynamic completer in spec Section 11.3 plus the
mid-token splitter in Section 11.5. Each completer is a Python module
under `src/kanon_cli/completions/` paired with `tests/unit/test_<name>.py`,
registered as a hidden `kanon __complete_<name>` subcommand in
`src/kanon_cli/cli.py`. Each completer is failure-quiet on stdout
(empty list) and failure-loud on stderr (structured entry to
`${KANON_CACHE_DIR}/completion-errors.log`).

Task ordering inside the story:

- **T1** -- `__complete_catalog_entries`
- **T2** -- `__complete_source_names_in_kanon`
- **T3** -- `__complete_names_in_lockfile`
- **T4** -- `__complete_catalog_versions` (factors the PEP 440 tag-name
  filter into a shared helper that T5 reuses)
- **T5** -- `__complete_project_versions <repo-url>` (depends on T4 for
  the shared PEP 440 filter)
- **T6** -- `__complete_cached_catalogs`
- **T7** -- mid-token splitter (shell helper in preamble + Python
  entry-name -> repo-url lookup); depends on T4 and T5 for the
  `__complete_project_versions` target the splitter routes to.

Every completer reads from local files or already-cloned cache only
(no network calls inline; the cache itself is populated by `kanon install`
or by the first cold tab-press bounded by `KANON_COMPLETION_TIMEOUT`,
both handled in E7-F3). Each task wires the cache helper from E7-F3-S1-T1
through E7-F3-S1-T5.

Spec source: spec Section 11.3 (dynamic completers table), 11.4
(caching), 11.5 (mid-token splitter), and 11.8 (testing requirements).
