## Description

Author the spec-required CI test that enforces kanon's
provider-agnostic invariant by greping the entire tracked source tree
for provider-specific CLI invocations and provider-specific REST or
GraphQL hostnames.

The test is a pytest module under `tests/functional/` so it runs as
part of the standard `pytest tests/functional -v` invocation. CI picks
it up automatically -- no separate workflow file is needed.

### What the test does

1. Enumerate the tracked file set via
   `subprocess.check_output(["git", "ls-files"], cwd=<repo_root>)`,
   decoding bytes to UTF-8 and splitting on `"\n"`. Use the
   `git ls-files` plumbing form so untracked working-tree files do not
   pollute the scan.
2. Compute the allowlist:
   - Always-allowlisted path prefixes (built into the test, not the
     allowlist file): `docs/`, `tests/fixtures/`, `.git/`. These cover
     the spec's blanket exemptions for docs files and fixtures.
   - The allowlist file `tests/integration/provider_allowlist.txt` is
     read and parsed line-by-line. Each non-empty, non-`#`-prefixed
     line MUST have the shape `<path>:<justification>` (a colon
     separator with non-empty justification text). Malformed lines
     raise `ValueError` naming the line number; the test fails fast.
   - The allowlist file is itself in the allowlist (the file contains
     the forbidden tokens as part of its documented format).
3. For each non-allowlisted tracked file: read the bytes, decode
   UTF-8 with `errors="replace"`, and scan line-by-line for the
   forbidden token set.
4. Forbidden CLI tokens are matched via the regex
   `r"\b(gh|glab|bb|tea)\b"` plus the literal substrings
   `"aws codecommit"` and `"az repos"`. Word-boundary matching ensures
   `right`, `weight`, `rubber`, `tearing`, and similar do not falsely
   fire.
5. Forbidden hostnames are matched via the literal substrings
   `api.github.com`, `gitlab.com/api`, `bitbucket.org/!api`, and
   `dev.azure.com/_apis`.
6. On any match: the test assertion fails with a message naming the
   file path (repo-relative), the 1-based line number, and the matched
   token, plus a remediation line:
   `Remediation: remove the provider-specific reference, OR add an
   exemption line to tests/integration/provider_allowlist.txt with a
   justification comment.`
7. When the allowlist file is empty (the day-one state of this Task),
   the test passes against the current tree because no
   provider-specific tokens exist in production code today.

### What the test does NOT do

This test does not shell out to any provider. It uses only `git
ls-files` (which is a local git plumbing command, not a provider call)
and the local filesystem.

### Test file structure

`tests/functional/test_provider_agnostic.py` parametrises the
forbidden-token cases so each token has its own test ID in the report:

```python
@pytest.mark.parametrize("token", FORBIDDEN_CLI_TOKENS + FORBIDDEN_HOST_TOKENS)
def test_no_forbidden_token_in_tracked_source(token, ...): ...
```

Plus a single integration-style test that enumerates all tracked
non-allowlisted files once and asserts zero findings across the
combined forbidden-token set, so the failure message reports all
matches in one run rather than one parametrised case at a time.

The allowlist parser is a private helper in the same module
(`_load_allowlist(repo_root: Path) -> set[str]`) with its own unit-
shaped tests that exercise:

- Empty file.
- File with only comments.
- File with `<path>:<justification>` lines.
- File with malformed line (no colon) -- raises `ValueError`.
- File with whitespace-only justification -- raises `ValueError`.

### Allowlist file format

`tests/integration/provider_allowlist.txt` (NEW, empty except for a
header comment):

```
# Provider-agnosticism allowlist.
#
# Format: <path>:<justification>
#   - <path>: repo-relative path of the file to exempt from the
#     provider-agnostic grep test.
#   - <justification>: non-empty free-text reason a human reviewer
#     accepted this exemption.
#
# Lines starting with `#` and blank lines are ignored.
#
# Adding an entry here requires a code review. The intent is that
# multi-provider parity test fixtures (per spec Section 10) and similar
# explicitly-labeled cross-provider cases live here with a clear
# justification. Production source code MUST NOT appear in this list.
```

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
