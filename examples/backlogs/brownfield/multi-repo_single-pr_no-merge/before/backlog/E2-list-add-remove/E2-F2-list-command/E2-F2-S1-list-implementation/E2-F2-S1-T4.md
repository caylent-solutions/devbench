## Description

Extend `kanon list` with the historical-versions walking mode and its
supporting controls per spec Section 4.1:

- `--all-versions`: walks historical catalog versions. For each version
  (sourced from `git ls-remote --tags` against the manifest repo), emits one
  `name@version` row per catalog entry per version walked. Tags whose last
  `/`-delimited path component is not a valid `packaging.version.Version`
  are SKIPPED with the loud-error path delegated to
  `_resolve_constraint_from_tags()` (E1-F1-S1-T2 already raises with the
  full skipped-tag list).
- `--limit N` / `--no-limit`: caps the number of versions walked. Default
  cap comes from new constant `KANON_LIST_LIMIT` (default `50`), settable
  via env var. `--no-limit` is equivalent to passing an arbitrarily large
  `--limit`.
- `--since-version <spec>`: filters the walked versions via a PEP 440
  constraint (e.g., `--since-version '>=1.0,<2.0'`). Implemented by feeding
  the cap-list through `_resolve_constraint_from_tags()`-style filtering.

New constant added to `src/kanon_cli/constants.py`:

- `KANON_LIST_LIMIT = 50` with env-var override.

Mutual exclusion:

- `--all-versions` is mutually exclusive with `--tree` (introduced by
  E2-F2-S1-T3); detected at argparse-validation time and surfaced as a
  hard error before any catalog work.

Ordering and output:

- Versions are ordered newest-first by `packaging.version.Version` natural
  sort. For each version, the per-entry rows are emitted in the same
  lexicographic order used by the default output.
- Per-row text format: `<entry-name>@<version>` (matches the worked-example
  in spec Section 4.1 "--all-versions worked example").
- `--format json` (E2-F2-S1-T5) renders the same data as a structured array
  of `{name, version, ref, sha}` objects; this task does NOT add the JSON
  shape (T5 owns it) but must record the resolved `ref` and `sha` per row
  in a structure that T5 can pick up.
