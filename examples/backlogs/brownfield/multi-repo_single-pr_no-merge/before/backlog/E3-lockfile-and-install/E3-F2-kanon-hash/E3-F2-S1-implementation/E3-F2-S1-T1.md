## Description

Author `src/kanon_cli/core/kanon_hash.py` containing:

- `kanon_hash(kanon_path: Path) -> str`: returns a deterministic SHA-256
  digest prefixed with `sha256:` over the normalised form of the `.kanon`
  file at `kanon_path`.

Algorithm (spec Section 5.1, verbatim):

1. Parse the `.kanon` file via the existing `parse_kanonenv` primitive.
2. Extract every `KANON_SOURCE_<name>_{URL,REVISION,PATH}` triple. Discard
   comments, blank lines, and any non-`KANON_SOURCE_*` keys (specifically
   `GITBASE`, `CLAUDE_MARKETPLACES_DIR`, and `KANON_MARKETPLACE_INSTALL`).
3. Sort triples by source name (lexicographic, case-sensitive); within a
   source, `URL` precedes `REVISION` precedes `PATH`.
4. Serialise as bytes `name\turl\trevision\tpath\n` per source. If any of
   `name`, `url`, `revision`, or `path` contains a literal tab, NUL byte,
   or newline, raise `KanonHashError` with a clear message naming the
   source and the bad character (by codepoint); this is a hard error, not
   a sanitisation.
5. SHA-256 the serialised bytes.
6. Return `f"sha256:{digest.hexdigest()}"`.

The function is pure: given identical `.kanon` content, it returns identical
bytes. It does not touch the filesystem outside reading `kanon_path` and
makes no network calls.

Required properties (each one is a parametrised unit test in this task):

- Re-ordering source blocks in `.kanon` does NOT change the hash.
- Adding or modifying comments does NOT change the hash.
- Adding or modifying blank lines does NOT change the hash.
- Changing any `REVISION` value DOES change the hash.
- Changing any `URL` value DOES change the hash.
- Changing any `PATH` value DOES change the hash.
- Changing a source name DOES change the hash.
- Adding or modifying `GITBASE`, `CLAUDE_MARKETPLACES_DIR`, or
  `KANON_MARKETPLACE_INSTALL` does NOT change the hash.
- A `URL` containing a literal tab raises `KanonHashError`.
- A `PATH` containing a literal newline raises `KanonHashError`.
- A `REVISION` containing a literal NUL byte raises `KanonHashError`.

This task has no upstream backlog dependencies. It uses only the existing
`parse_kanonenv` primitive that ships in today's kanon codebase.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 5.1
(Lockfile consistency hash) including the properties list and the relationship
note explaining that `kanon_hash` covers ONLY the `.kanon` triples and is
independent of the `[catalog].source` lockfile field.
