## Description

Author `src/kanon_cli/core/lockfile.py` containing the schema v1 dataclass
tree plus the two public entry points:

- `read_lockfile(path: Path) -> Lockfile`: parse a TOML file from disk into
  the dataclass tree, applying every validation rule in spec Section 5
  (resolved-SHA hex-length check; revision-spec PEP 440 / `refs/...` /
  branch-charset regex; `canonical_url` equals `canonicalize_repo_url(url)`;
  `path` and `path_in_repo` reject embedded NUL / newline / tab characters).
  Validation failures raise specific exceptions (`LockfileSchemaError`,
  `LockfileValidationError`) with messages naming the offending field, the
  unparseable value, and the operator's likely remediation step.
- `write_lockfile(lockfile: Lockfile, path: Path) -> None`: serialise the
  dataclass tree back to TOML and atomically replace the target path using
  a write-temp-then-rename pattern in the same directory (so the rename is
  on the same filesystem). The temp file uses a `.tmp.<pid>.<rand>` suffix
  so two concurrent writers do not collide on the temp path.

The dataclass tree mirrors the TOML schema exactly:

- `Lockfile`: `schema_version: int`, `generated_at: str` (ISO-8601 UTC),
  `generator: str` (e.g., `"kanon-cli/1.4.0"`), `kanon_hash: str`,
  `catalog: CatalogBlock`, `sources: list[SourceEntry]`.
- `CatalogBlock`: `source: str` (the `<url>@<ref>` form),
  `url: str`, `revision_spec: str`, `resolved_ref: str`, `resolved_sha: str`.
- `SourceEntry`: `name: str`, `url: str`, `revision_spec: str`,
  `resolved_ref: str`, `resolved_sha: str`, `path: str`,
  `includes: list[IncludeEntry]`, `projects: list[ProjectEntry]`.
- `IncludeEntry`: `name: str`, `path_in_repo: str`, `url: str`,
  `resolved_sha: str`, `includes: list[IncludeEntry]` (recursive, unbounded
  depth).
- `ProjectEntry`: `name: str`, `url: str`, `canonical_url: str`,
  `revision_spec: str`, `resolved_ref: str`, `resolved_sha: str`.

This task also adds `KANON_LOCK_FILE = "KANON_LOCK_FILE"` to
`src/kanon_cli/constants.py` (the env-var name; the value is the operator's
override path). The constant lives next to the existing
`KANON_KANON_FILE` constant so the env-var surface is grouped.

Validation specifics:

- `resolved_sha` must match `^[a-f0-9]{40}$` OR `^[a-f0-9]{64}$` (SHA-1 OR
  SHA-256 git object IDs). Uppercase hex is rejected; mixed-case is
  rejected; non-hex is rejected.
- `revision_spec` is accepted if it satisfies any one of: parses as
  `packaging.requirements.SpecifierSet` (e.g., `==1.0.0`, `~=2.0.0`,
  `>=1.0,<2.0`); starts with `refs/` (literal git ref); matches the
  branch-name regex `^[a-zA-Z0-9_./+-]+$`. PEP 440 specs MAY carry a
  monorepo path prefix (`subpackage/==1.0.0`); the prefix is stripped
  before SpecifierSet parsing.
- `canonical_url` on every `ProjectEntry` is compared via string equality to
  `canonicalize_repo_url(entry.url)`. Mismatch is
  `LockfileValidationError`.
- `path` and `path_in_repo` strings are checked for `\x00`, `\n`, `\t`; any
  occurrence raises `LockfileValidationError`.

Schema migration policy is in scope for T2; this task only handles
`schema_version == 1` and raises `LockfileSchemaError` for any other value
with the message "lockfile schema v<N> not supported by this kanon
version".

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 5
(Lockfile format and validation rules) and Section 4.7.1 (atomicity
contract for the lockfile writer).

### Approach

1. **TDD RED:** Author `tests/unit/test_lockfile.py` with parametrised
   cases for every validation rule listed in the Description. RED phase
   confirms every test fails against an absent `src/kanon_cli/core/lockfile.py`
   (`ImportError`).
2. **TDD RED (integration):** Author
   `tests/integration/test_lockfile_roundtrip.py` with a property-style
   case that constructs a `Lockfile` dataclass in memory, writes it to a
   `tmp_path`-scoped file, reads it back, and asserts deep equality. The
   roundtrip test exercises the atomic write + rename codepath against the
   real filesystem.
3. **TDD GREEN (dataclasses):** Author the `Lockfile`, `CatalogBlock`,
   `SourceEntry`, `IncludeEntry`, `ProjectEntry` dataclasses with the field
   types listed in the Description. Re-run the unit tests; the dataclass
   construction tests pass.
4. **TDD GREEN (reader):** Implement `read_lockfile(path)` using the
   stdlib `tomllib` module (Python 3.11+). Each validation rule is a small
   helper function under the module's private namespace
   (`_validate_resolved_sha`, `_validate_revision_spec`,
   `_validate_canonical_url`, `_validate_path_chars`). Each helper raises
   `LockfileValidationError` with the standard error shape (Section 4).
5. **TDD GREEN (writer):** Implement `write_lockfile(lockfile, path)`
   using `tomli_w` (already in pyproject.toml dependencies if present,
   otherwise added). Atomic write via `tempfile.NamedTemporaryFile(dir=path.parent, delete=False)`
   followed by `os.replace(tmp_path, path)`. The temp file is closed
   before rename; the temp file's permissions are set to match the
   destination's expected mode before rename.
6. **TDD GREEN (constants):** Add `KANON_LOCK_FILE = "KANON_LOCK_FILE"`
   to `src/kanon_cli/constants.py` adjacent to the existing
   `KANON_KANON_FILE`.
7. **TDD REFACTOR:** Extract any shared validation helpers (e.g., the
   resolved-SHA regex check) into the module's private namespace if used
   by more than one validator.
8. **Docs:** Update `docs/lockfile.md` (NEW per spec Section 8) with the
   v1 schema definition, the validation rules, and a worked example
   matching the spec Section 5 listing.
9. **Verify:** `uv run pytest tests/unit/test_lockfile.py tests/integration/test_lockfile_roundtrip.py -v`,
   then the full suite: `uv run pytest tests/ -v && uv run ruff check src tests && uv run ruff format --check src tests && uv run mypy src && uv run bandit -r src -ll`.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
