## Description

Implement transitive `<include>` resolution with cycle detection AND
diamond support during `kanon install`. Today's resolver walks
`<include>` chains, but the cycle and diamond cases are not explicitly
defined. Spec Section 4.7 mandates:

- **Cycle detection**: walking `<include>` chains depth-first, the
  resolver tracks visited XML paths (canonicalised). When the walk
  re-visits a node that is already on the active path, the resolver
  raises `IncludeCycleError` with a message rendering the cycle as
  `A.xml -> B.xml -> A.xml` (the closing edge that detected the cycle
  is rendered explicitly so the operator sees where the loop closes).
- **Diamond handling**: when the walk re-visits a node that has already
  been fully processed (i.e., it is in the "done" set, not the "active
  path" set), the resolver deduplicates and continues; the second visit
  is a no-op for `<include>` traversal but the project rows below the
  shared include are STILL processed under both paths' contexts (which
  is fine because diamonds resolve to the same SHAs).

The canonical path used as the dedup key is the resolved absolute path
inside the manifest repo (e.g., `repo-specs/git-connection/remote.xml`),
not the relative `<include name=...>` attribute value (which can differ
between callers). Canonicalisation strips `./` segments, resolves `..`
segments, and normalises path separators per stdlib `os.path.normpath`.

Implementation surface:

- Add `_walk_includes(start_xml_path: Path, manifest_repo: Path) ->
  IncludeTree` helper in `core/install.py` (or in a new helper module
  `core/include_walker.py` if it keeps `install.py` from sprawling).
  The walker uses two sets: `active_path: list[Path]` (stack of
  ancestors on the current DFS branch) and `done: set[Path]` (paths
  whose subtree has been fully processed). Pre-visit: if the next path
  is in `active_path`, raise `IncludeCycleError` with the rendered
  cycle. If it is in `done`, skip (diamond dedupe). Otherwise push to
  `active_path`, recurse, pop, add to `done`.
- Add `IncludeCycleError(InstallError)` exception class.
- Add `IncludeTree` dataclass: `path: Path`, `includes: list[IncludeTree]`,
  `projects: list[ResolvedProject]`. The walker returns the root of this
  tree; downstream lockfile-writing code serialises it into the nested
  `[[sources.includes]]` TOML structure.
- The walker's output drives lockfile serialisation: nested
  `[[sources.includes]]` entries match the depth and order of the DFS
  walk; diamond-deduped duplicates appear only at their first
  encountered position (a comment in the lockfile-write helper notes
  this).

The error message format for cycles renders every node in order:
`"include cycle: <p0> -> <p1> -> ... -> <pn> -> <p0>"` where `p0` is the
node that closed the cycle. The path list uses repo-relative paths (not
absolute filesystem paths) so the message is portable across operator
machines.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.7
"`<include>` cycle detected" and "`<include>` diamond" rows; Section 5
(lockfile format) for the nested `[[sources.includes]]` structure.

### Approach

1. **TDD RED (unit):** Author `tests/unit/test_include_walker.py`
   with parametrised cases: (a) flat single XML (zero includes) -> tree
   has root only; (b) two-level chain A -> B -> C -> tree depth 2; (c)
   cycle A -> B -> A -> `IncludeCycleError` rendered correctly; (d)
   diamond A includes B and C, both B and C include D -> tree has D
   appearing only once at its first-walked position; (e) self-include A
   -> A is a one-cycle, rendered as `A.xml -> A.xml`.
2. **TDD RED (integration):** Author
   `tests/integration/test_install_include_cycle.py` and
   `tests/integration/test_install_include_diamond.py` exercising the
   walker against real manifest-repo fixtures placed in `tmp_path`. The
   cycle fixture creates three XML files forming a triangle; the diamond
   fixture creates four files forming a diamond.
3. **TDD GREEN:** Implement the walker in
   `src/kanon_cli/core/include_walker.py` (new module to keep
   `install.py` from sprawling). Implement `IncludeCycleError` and
   `IncludeTree` dataclasses. Re-export from `core/install.py` if
   call-sites prefer that import path.
4. **TDD GREEN (lockfile wiring):** Update `install.py`'s
   lockfile-serialisation step to consume the `IncludeTree` and produce
   the nested `[[sources.includes]]` TOML structure that
   E3-F1-S1-T1's writer expects.
5. **TDD REFACTOR:** Extract the `os.path.normpath`-based
   canonicalisation as a `_canonicalize_include_path(path: Path) -> Path`
   helper for DRY (it is reused on every walk step).
6. **Docs:** Update `docs/lockfile.md` with the include-tree
   serialisation rule and the diamond-dedupe note; update
   `docs/architecture.md` with the cycle-detection algorithm.
7. **Verify:** Full suite.
