# E1-F5: Provider-agnosticism CI test (tree-wide grep)

## Status: in-queue

## Description

Add the spec-required CI test that enforces kanon's provider-agnostic
invariant by greping the entire source tree for provider-specific CLI
invocations and provider-specific REST/GraphQL hostnames. Any match
fails the build.

This feature closes the GAP between the spec (Section 10 line 1023 and
Section 12 acceptance item 20) and the existing backlog: today, the
"provider-agnostic" invariant is documented (`docs/security-model.md`,
the Code Standards block, spec Section 3.6) but NOT enforced
programmatically. E1-F5 adds the enforcement test.

The test lives in `tests/functional/test_provider_agnostic.py` and runs
as part of the normal `pytest tests/functional` invocation, so CI picks
it up automatically without a separate workflow file. It enumerates
tracked files via `git ls-files`, filters out the allowlist (docs files,
test fixtures, and any path enumerated in
`tests/integration/provider_allowlist.txt`), and scans each remaining
file for the forbidden tokens.

Forbidden tokens:

- CLI tools (word-boundary matched): `\bgh\b`, `\bglab\b`, `\bbb\b`,
  `\btea\b`, `aws codecommit`, `az repos`.
- Hostnames (literal): `api.github.com`, `gitlab.com/api`,
  `bitbucket.org/!api`, `dev.azure.com/_apis`.

The allowlist file (`tests/integration/provider_allowlist.txt`) is a
new in-repo file with a documented format (`<path>:<justification>`
per line). It is empty at creation time -- the test must pass against
the current tree because no provider-specific tokens exist today. Any
future need to allow a provider token requires a human-reviewed PR
that adds a line with a justification comment.

On a match, the test emits a clear, actionable failure naming the file,
line number, and matched token, plus the remediation step (file an
exemption in `tests/integration/provider_allowlist.txt` with a
justification, OR remove the provider-specific reference from the
source).

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 0
header (line 6, provider-agnostic invariant), Section 3.6 (trust model
trust-model), Section 10 line 1023 (CI grep test requirement), Section
12 acceptance item 20 (provider-agnostic enforcement), Section 14
references to provider-agnosticism.
