## Description

Implement the core `kanon outdated` command surface as a new module
`src/kanon_cli/commands/outdated.py`. The command:

1. **Resolves the catalog** (required; no lockfile fallback for `outdated` per spec Section 4.4
   behaviour 1). Catalog source precedence: `--catalog-source` CLI flag, then
   `KANON_CATALOG_SOURCE` env var. If neither is set, hard error with the standard
   `ERROR: <one-line summary>` + remediation shape (operator must pass `--catalog-source` or
   export `KANON_CATALOG_SOURCE`).
2. **Reads the `.kanon` file** at `--kanon-file` (default from `KANON_KANON_FILE`,
   constant default `./.kanon`).
3. **Reads `.kanon.lock`** at `--lock-file` if present (default derived from `--kanon-file`). The
   lockfile is OPTIONAL for `outdated`: when present, it provides the `current` resolved SHA; when
   absent, the command live-resolves against the catalog.
4. **For each `KANON_SOURCE_<name>_*` block** (parsed via the existing
   `core/kanonenv.py::parse_kanonenv`), computes three columns:
   - **current** -- from the lockfile when present (the locked SHA), else live-resolved via the
     resolver (calls `version.py::resolve_version` with the source's URL + REVISION).
   - **latest-matching-spec** -- the latest ref under the source's prefix that satisfies the
     source's REVISION spec, via `version.py::_resolve_constraint_from_tags`.
   - **latest-available** -- the latest ref under the source's prefix ignoring the spec
     (equivalent to a `*` constraint applied to the same prefix).
5. **Emits one row per source** in `name | current | latest-matching-spec | latest-available |
   upgrade-type` format. Default format `table` (controlled by `KANON_OUTDATED_FORMAT`); JSON
   output is added in E4-F1-S1-T4. The `upgrade-type` column reads `none`, `patch`, `minor`,
   `major`, or `prerelease`, derived by comparing `current` to `latest-matching-spec` via
   `packaging.version.Version`. Branch-pinned sources are added in E4-F1-S1-T2 (this task keeps
   them resolving as if tag-pinned; the dedicated branch logic lands in T2). For this task, every
   row in the test fixtures uses tag-pinned sources only.

This task scopes ONLY to tag-pinned sources. Branch-pinned columns (T2), `--fail-on-upgrade` (T3),
and `--format json` (T4) are scoped to follow-up tasks within the same story. T1 lands:

- The `outdated.py` module with a `run(args)`-shaped function and a registration entry point.
- The subcommand wiring in `src/kanon_cli/cli.py` (under the existing argparse subparsers registry,
  reusing the shared `--catalog-source` / `--kanon-file` / `--lock-file` flag definitions from
  `core/cli_args.py`).
- The `KANON_OUTDATED_FORMAT` constant in `src/kanon_cli/constants.py` (default value `"table"`)
  and the `--format` flag wiring with `choices=("table",)` for this task (extended to
  `("table", "json")` in T4).
- Exit code 0 always for this task (T3 introduces `--fail-on-upgrade`).

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.4 (behaviour 1-3) and Section 7
(`KANON_OUTDATED_FORMAT`, `--catalog-source`, `--kanon-file`, `--lock-file`, `--format`).

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
