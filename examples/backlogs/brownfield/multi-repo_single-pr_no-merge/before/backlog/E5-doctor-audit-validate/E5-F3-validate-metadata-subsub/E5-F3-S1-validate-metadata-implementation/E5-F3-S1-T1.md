## Description

Add a new sub-subcommand `kanon validate metadata` to the existing
`kanon validate` command. Modifies `src/kanon_cli/commands/validate.py`
to register `metadata` alongside today's `xml` and `marketplace`
sub-subcommands. The new sub-subcommand runs the in-repo subset of
soft-spot checks from spec Section 3.5 (rules 1, 2, 3) without network
or clone:

- **Soft-spot 1 (REQUIRED + RECOMMENDED `<catalog-metadata>` fields).**
  Errors on missing REQUIRED fields, duplicate child elements within
  one `<catalog-metadata>` block, and multiple `<catalog-metadata>`
  blocks per XML file. Warns on missing RECOMMENDED fields. Same field
  lists used by `kanon catalog audit --check metadata` (E5-F2-S1-T2)
  via the shared constants `KANON_CATALOG_METADATA_REQUIRED_FIELDS`
  and `KANON_CATALOG_METADATA_RECOMMENDED_FIELDS`.
- **Soft-spot 2 (source-name derivation).** Warns when the normalised
  form differs from the entry name, AND warns when the entry name
  contains characters outside `[a-zA-Z0-9_-]`. Same rule used by
  `kanon catalog audit --check source-name-derivation` (E5-F2-S1-T3).
- **Soft-spot 3 (entry-name uniqueness).** Errors on collisions
  across XML files in the repo. Same rule used by `kanon catalog audit
  --check entry-name-uniqueness` (E5-F2-S1-T4).

Argparse surface:

- `kanon validate metadata [--repo-root <path>] [--format {text,json}]
  [--no-color]`
- `--repo-root` defaults to cwd; matches the existing `kanon validate
  xml` and `kanon validate marketplace` siblings.
- `--format` defaults to `text` (matches `marketplace`'s output style).
  `json` emits the same `{"findings": [...]}` schema as `kanon catalog
  audit`.

Exit code semantics (matches `kanon validate marketplace`):

- Exit 0 if no ERROR findings, regardless of warnings.
- Exit 1 if any ERROR finding.
- `--strict` is NOT introduced by this task. Catalog authors who want
  strict semantics use `kanon catalog audit --strict`.

What this sub-subcommand does NOT do:

- It does NOT check soft-spot 4 (`<remote>` resolvability) or soft-spot
  5 (PEP 440 tag-name compliance). Those require resolving include-chains
  through git or running `git ls-remote --tags`; they live in `kanon
  catalog audit`.
- It does NOT clone. No network access. Reads ONLY
  `repo-specs/**/*-marketplace.xml` inside `--repo-root`.

DRY: T2/T3/T4 of E5-F2 already implement the soft-spot check functions
(`_check_metadata`, `_check_source_name_derivation`,
`_check_entry_name_uniqueness`) inside `catalog.py`. This task imports
the same three functions from `catalog.py` and invokes them from
`validate.py::validate_metadata_command(args)`. If `catalog.py`'s
check functions accept a `target_path` they can be reused without
adaptation; otherwise expose them via a shared module
`src/kanon_cli/core/audit_checks.py` so both command surfaces consume
the same implementation.

Source-test atomicity: this task modifies `validate.py` (existing) and
adds new tests. AC-FINAL-014 applies to the lines this task adds.

Spec source: spec Section 3.5 (soft-spot rules) and the introductory
paragraph naming `kanon validate metadata`; Section 13 decision 10;
Section 1.1 (terminology).

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
