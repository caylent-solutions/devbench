## Description

Add the filter framework to `kanon list` per spec Section 4.1 flag-table
rows `<substring>` (positional), `--regex <pattern>`, `--match-fields <csv>`:

- Positional `<substring>` argument: filter catalog entries by case-sensitive
  substring against the entry's `name`, `display-name`, `description`, and
  `keywords` (all four fields, default match-set).
- `--regex <pattern>`: alternative to the positional substring; same default
  match-set; uses Python `re.search` against each field's value
  (`keywords` matches against any element).
- `--match-fields <csv>`: comma-separated list of one or more of
  `name,display-name,description,keywords`; restricts the filter to that
  subset. Default (when `--match-fields` is NOT supplied) is all four fields.
- Mutual-exclusion rules:
  - `<substring>` and `--regex` are mutually exclusive; supplying both is a
    hard error at argparse-validation time.
  - `--match-fields` REQUIRES `<substring>` or `--regex`; supplying
    `--match-fields` without either is a hard error.
  - Unknown values inside the `--match-fields` CSV are a hard error
    listing the legal set.
- Zero-match behaviour (spec Section 4.1 "Zero-match behavior"): exit 0 with
  empty stdout and a single-line stderr note "0 entries match filter" so
  human invocations get feedback while pipelines stay clean. The note text
  matches the spec's canonical phrasing.

The filter applies BEFORE rendering, so the same filter affects every
output mode (default names, `--detail`, `--tree`, `--all-versions`,
`--format json`). The threshold guardrail in E2-F2-S1-T3 already treats a
supplied filter as the "filter is present" signal; this task delivers the
matching positional+regex inputs so that path completes.
