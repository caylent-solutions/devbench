# E6-F2: Bundled `src/kanon_cli/catalog/` removal and resolver fallback cleanup

## Status: in-queue

## Description

Delete the bundled `src/kanon_cli/catalog/` directory tree from the
kanon wheel, add a repo / CI guard that fails the build if the
directory reappears, and remove the third-tier "bundled fallback"
path inside `src/kanon_cli/core/catalog.py::resolve_catalog_dir`
(today's lines 40-49, the `_get_bundled_catalog_dir()` return).

After this feature lands:

- The wheel no longer ships the bundled catalog (one entry, `kanon`,
  used for self-bootstrap). The self-bootstrap path is dead because
  E6-F1 already replaced `kanon bootstrap kanon` with a shim that
  exits 3.
- `resolve_catalog_dir(None)` (called when neither
  `--catalog-source` nor `KANON_CATALOG_SOURCE` is set) raises the
  canonical missing-catalog error from spec Section 4 (verbatim text
  ending with `See docs/catalogs-explained.md ...`) instead of
  silently returning the bundled directory.
- The private helper `_get_bundled_catalog_dir()` is deleted (no
  consumers after the fallback path is removed).
- A repo-side guard rejects any future commit that re-introduces
  `src/kanon_cli/catalog/`.

Feature scoped into two tasks (one story) so the wheel-layout change
can be reviewed independently from the resolver behaviour change:

- **T1**: delete `src/kanon_cli/catalog/` directory tree; verify
  `pyproject.toml` does not list the catalog dir under package-data;
  add a wheel-layout test asserting the built wheel does not contain
  `catalog/`; add an integration test asserting no bundled catalog
  is loadable at runtime.
- **T2**: remove the `_get_bundled_catalog_dir()` fallback from
  `resolve_catalog_dir`; delete the helper function; emit the
  canonical missing-catalog error instead.

Dependency wiring inside F2: T2 depends on T1 (the fallback removal
is observable from the outside, but the helper still exists in T1's
intermediate state; T2 deletes the helper after T1 confirms zero
filesystem usage). F2's first task depends on E6-F1-S1-T1 because
the shim must be in place before the bundled catalog is deleted,
otherwise the existing `kanon bootstrap kanon` self-bootstrap flow
breaks at runtime (the shim's no-boundary-call rule means the shim
exits 3 BEFORE touching the catalog, so the bundled-tree deletion
is then safe).

Spec source:
- `spec/kanon-list-add-lock-features-spec.md` Section 0.3 ("the
  bundled `src/kanon_cli/catalog/` directory is deleted alongside
  the shim").
- `spec/kanon-list-add-lock-features-spec.md` Section 4 header
  ("The bundled `src/kanon_cli/catalog/` directory is deleted by
  this spec's bootstrap-deprecation epic; the existing third-tier
  'bundled fallback' in `resolve_catalog_dir()` is removed at the
  same time.").
- `spec/kanon-list-add-lock-features-spec.md` Section 1 context
  bullet 3 ("the bundled `src/kanon_cli/catalog/` is deleted from
  the kanon wheel").
- `spec/kanon-list-add-lock-features-spec.md` Section 13 decision
  19 (no default manifest repo / no implicit default catalog source).
