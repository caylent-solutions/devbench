# E4-F1-S1-T2: Branch-pinned source columns -- drift detection and 12-char SHA truncation

## Status: in-queue

## Target Repository

## Description

Extend `src/kanon_cli/commands/outdated.py` (created in E4-F1-S1-T1) to handle sources whose
REVISION is a branch name rather than a PEP 440 spec or a SHA. Per spec Section 4.4 "Branch-pinned
sources" paragraph:

- A source's REVISION is "branch-pinned" when it is neither a PEP 440 version specifier (per
  `version.py::is_version_constraint`) nor a SHA-shaped string (40 or 64 hex chars) nor a
  `refs/tags/...` ref. The most common shapes: `main`, `develop`, `release/v1`, `feature/foo`.
- For branch-pinned sources, both the `latest-matching-spec` and `latest-available` columns
  display the current HEAD SHA of that branch, truncated to **exactly 12 characters** of the
  hexadecimal SHA. The truncation is the leading 12 chars (matching `git`'s short-SHA convention).
- The HEAD SHA is obtained via `git ls-remote <url> refs/heads/<branch>` and parsed from the
  single-line output. Subject to `KANON_RESOLVE_TIMEOUT` (default 30s) and the existing
  `KANON_GIT_RETRY_COUNT` retry policy.
- The `upgrade-type` column reads `drift` when the locked SHA in `.kanon.lock` (the `current`
  column) differs from the branch HEAD SHA (the `latest-matching-spec` column). When the locked
  SHA equals the branch HEAD or when no lockfile is present, `upgrade-type` reads `none`.
- There is **no** "latest available across all branches" notion in the spec. Operators who want
  cross-branch upgrade visibility must switch to tag-based pinning. This means
  `latest-matching-spec == latest-available` for every branch-pinned row (both display the same
  truncated SHA).

T2 amends the `_build_row(source, lock_entry, catalog)` helper from T1 to branch on the source's
REVISION shape: tag-pinned -> T1 logic; branch-pinned -> the new branch-HEAD-SHA logic; SHA-pinned
-> a third path where all three columns read the same SHA (truncated for `latest-*`; `upgrade-
type` is always `none`). The third path (SHA-pinned) is included here because the spec does not
spell out a separate behaviour for it and the natural reading of Section 4.4 is that a pinned SHA
cannot drift (the operator pinned exactly that SHA on purpose).

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.4 "Branch-pinned sources"
paragraph.

   (a) branch-pinned source whose locked SHA equals branch HEAD -> `upgrade-type=none`, both
