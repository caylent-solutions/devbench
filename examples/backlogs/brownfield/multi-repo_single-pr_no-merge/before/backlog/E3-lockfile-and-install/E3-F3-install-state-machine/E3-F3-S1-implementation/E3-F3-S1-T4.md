## Description

Add two boolean strictness flags to `kanon install`. Both default `False`
(today's behaviour is preserved); when present, they upgrade specific
notice-level events to hard errors per spec Section 4.7:

- `--strict-lock`: Upgrade "orphaned lock entry" notices to hard errors.
  An orphaned lock entry is a `[[sources]]` row in `.kanon.lock` whose
  `name` no longer appears in `.kanon` (the operator removed the source
  from their consumer state via `kanon remove`). Default behaviour
  (without `--strict-lock`): prune the orphaned entry from the rewritten
  lockfile and emit an info-line `"pruned orphaned lock entry: <name>"`
  per orphan. With `--strict-lock`: raise `OrphanedLockEntryError`
  listing every orphaned entry; remediation is "run `kanon install`
  without `--strict-lock` to prune, or restore the missing
  `KANON_SOURCE_<name>_*` triples in `.kanon`."
- `--strict-drift`: Upgrade "branch drift" notices to hard errors. Branch
  drift is the case where the lockfile records a SHA for a
  `revision_spec` that is a branch name (e.g., `main`), but the branch's
  current tip on remote is a different SHA. Default behaviour (without
  `--strict-drift`): reuse the locked SHA, emit info-line `"branch drift:
  <source>: <branch> tip <new-sha> differs from locked <old-sha>; reusing
  locked SHA"`. With `--strict-drift`: raise `BranchDriftError` listing
  every drift; remediation is `kanon install --refresh-lock-source
  <source>` to accept the new tip.

Both flags are independent boolean flags; either may be set without the
other; both may be set together.

Implementation surface:

- Add `--strict-lock` and `--strict-drift` argparse flags
  (`action="store_true"`); thread through to `core/install.py::install`
  as `strict_lock: bool = False` and `strict_drift: bool = False`.
- Add `OrphanedLockEntryError(InstallError)` and
  `BranchDriftError(InstallError)` exception classes (subclasses of the
  base `InstallError` T1 introduced).
- Add `_detect_orphaned_lock_entries(lockfile, kanon_sources) ->
  list[str]` helper returning the list of orphaned source names.
- Add `_detect_branch_drift(lockfile, resolver) ->
  list[BranchDriftReport]` helper. Each report carries source name,
  branch name, locked SHA, current-tip SHA. The helper consults the
  resolver's `git ls-remote` results that the install path already
  produces for branch-shaped `revision_spec` values.
- Wire both checks into the consistent-state branch from T1: the
  consistent-state path now (a) detects orphans + applies prune-or-error
  per the flag, (b) detects drift + applies reuse-or-error per the flag.

The drift detector runs only on the consistent state (the locked SHAs
are trustworthy there). On the hash-mismatch and refresh paths, drift is
not relevant because the lockfile is being rewritten anyway. On the
lockfile-absent path, there is no lockfile to compare against.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.7
state-matrix rows for branch drift and orphaned lock entries, plus the
flags table rows for `--strict-lock` and `--strict-drift`.
