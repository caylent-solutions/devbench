# E5-F3: `kanon validate metadata` sub-subcommand (in-repo soft-spot checks)

## Status: in-queue

## Description

Add a new sub-subcommand `kanon validate metadata` alongside today's
`kanon validate xml` and `kanon validate marketplace`. Modifies
`src/kanon_cli/commands/validate.py` to register the new sub-subcommand.

Where `kanon catalog audit` (E5-F2) is the consumer-side audit that can
clone a remote `<url>@<ref>` catalog and runs all five soft-spot checks
plus PEP 440 tag-name checks, `kanon validate metadata` is the
**in-repo** check for catalog authors editing their manifest repo
locally:

- Runs soft-spot 1 (required + recommended `<catalog-metadata>` fields,
  duplicate-child detection, multiple-block detection).
- Runs soft-spot 2 (source-name derivation warnings).
- Runs soft-spot 3 (entry-name uniqueness across XML files in the repo).
- Does NOT clone. No network. Reads ONLY `repo-specs/**/*-marketplace.xml`
  inside the supplied `--repo-root` (defaults to cwd).
- Does NOT check remote-url resolvability (soft-spot 4) or PEP 440 tag-name
  compliance (soft-spot 5); those require network and live in
  `kanon catalog audit`.

Mirrors the `--repo-root` flag and the `--format` / `--no-color` flags
from the sibling sub-subcommands `kanon validate xml` and `kanon validate
marketplace`.

Spec source: spec Section 3.5 paragraph ("Today's de-facto convention has
soft spots that need to be codified into the open-source standard,
enforced by: `kanon validate metadata` (NEW sub-subcommand under existing
`kanon validate`; sits alongside `kanon validate xml` and `kanon validate
marketplace`)") and Section 13 decision 10.
