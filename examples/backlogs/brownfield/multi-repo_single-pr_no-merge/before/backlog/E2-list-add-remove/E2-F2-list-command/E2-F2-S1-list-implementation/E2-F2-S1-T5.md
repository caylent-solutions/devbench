## Description

Add the `--format` flag to `kanon list` per spec Section 4.1.

- Flag: `--format {names,json}` with default `names`.
- Env var: `KANON_LIST_FORMAT` (precedence: CLI flag > env var > default).
- `names` is today's default behaviour (one entry name per line, or one
  `<entry-name>@<version>` row per line under `--all-versions`).
- `json` emits a structured array. Two shapes per spec:
  - Default mode + `--detail` mode: array of objects mirroring the
    `<catalog-metadata>` fields surfaced by `--detail`
    (`{name, display-name, type, description, version}`). The same array
    shape is used for both default (no `--detail`) and detail modes; the
    consumer reads only the fields they need.
  - `--all-versions` mode: array of `{name, version, ref, sha}` objects per
    spec Section 4.1 worked-example footer.

Output is emitted to stdout as a single JSON document (no trailing newline
beyond the standard one). Streaming is preserved by buffering only one
record at a time during walking and serialising the final list atomically
(per the JSON-object boundary requirement). For very-large catalogs this
means the JSON path holds the per-entry index in memory; the stream-per-line
form is preserved for `names` format only.

Interactions with prior tasks:

- `--format json` with `--detail` is allowed and is the spec-recommended
  machine-consumption shape.
- `--format json` with `--tree` is currently undefined in the spec. This
  task treats it as a hard error (`--format json` is incompatible with
  `--tree`) and surfaces the conflict at argparse-validation time. The
  spec Section 4.1 worked-example list for JSON output names only the
  default and `--all-versions` shapes; `--tree` is left for a future
  release.
