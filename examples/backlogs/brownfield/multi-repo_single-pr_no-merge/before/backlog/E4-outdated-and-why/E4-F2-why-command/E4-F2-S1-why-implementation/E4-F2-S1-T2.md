## Description

Extend `src/kanon_cli/commands/why.py` (created in E4-F2-S1-T1) to implement the full three-
category argument-to-node matching precedence from spec Section 4.5 step 2, plus the ambiguity
hard-error from step 3.

Argument-to-node matching expands from T1's URL-only path to all three categories:

- **(a) `<project>` repo URL.** Canonicalized via `core/url.py::canonicalize_repo_url`. Match
  against every `<project>` node's canonicalized URL. (T1 behaviour, preserved.)
- **(b) Transitive XML manifest path.** e.g., `repo-specs/git-connection/remote.xml`. Match
  against every `<include>` node's resolved manifest-relative path.
- **(c) Top-level source name.** A `KANON_SOURCE_<source-name>_*` key from the `.kanon` file.
  Match via `derive_source_name()` (E2-F3) so case + dash/underscore normalization is canonical:
  argument `Foo-Bar` matches source-name token `foo_bar` after normalization.

**Match precedence** is NOT a stop-at-first-match strategy. All three categories are evaluated.
Then:

- Zero matches across all categories -> not-found error (T3 adds the Levenshtein closest-match
  suggestion to this error path; T2 keeps the bare error from T1).
- Exactly one match (in any single category) -> chain-walker runs against the matched node and
  prints its chains (the T1 path).
- Matches in TWO OR MORE categories -> hard error listing all matching interpretations. The error
  message names each category and the matched value, telling the operator how to disambiguate
  (e.g., "this argument matches both source name `foo` and project URL `file:///fixtures/foo`;
  pass the URL with explicit canonical form to disambiguate"). Exit code non-zero.

The ambiguity case is spec'd as "extremely unlikely but possible with `file://` test fixtures"
(Section 4.5 step 3). The integration test in this task forces ambiguity using exactly that
pattern: a `file://` URL whose path happens to equal an XML manifest path.

T2 also implements the XML-path match category (which T1 deliberately deferred). XML-path matching
is exact-string equality against the manifest-relative path string stored on each `<include>`
node.

Source-name matching uses `derive_source_name(arg)` to normalize the argument, then compares
against the normalized set of `KANON_SOURCE_*` keys from `.kanon`. The source-name match resolves
to the top-level source node in the tree.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.5 step 2 (full precedence list)
and step 3 (ambiguity hard error).

### Approach

1. **TDD RED (unit):** Author `tests/unit/test_why_ambiguity.py` with parametrized cases:
   (a) argument matches an XML manifest path only -> chain printed for the include's downstream
   tree; (b) argument matches a source name only (via `derive_source_name`) -> chains printed for
   that source; (c) argument matches both source name AND project URL -> hard error listing both;
   (d) argument matches XML path AND source name -> hard error listing both; (e) argument matches
   all three categories -> hard error listing all three; (f) `derive_source_name` normalization
   parity: argument `Foo-Bar` matches source `foo_bar` (and vice versa); (g) zero matches ->
   not-found error (unchanged from T1). Run; confirm RED.
2. **TDD GREEN (unit):** Extend `why.py`'s match-resolution stage from T1 (URL-only) to evaluate
   all three categories and collect every hit. If `len(hits) == 0` -> the existing not-found
   error. If `len(hits) == 1` -> dispatch to chain-walker (T1's path). If `len(hits) >= 2` ->
   raise a structured ambiguity error listing every interpretation. Re-run; confirm GREEN.
3. **TDD RED (integration):** Author `tests/integration/test_why_ambiguous.py` with an end-to-
   end fixture that intentionally forces ambiguity using `file://` URLs: a manifest XML at
   `repo-specs/foo/foo.xml` is included from a top-level XML, AND the `.kanon` declares a source
   named `repo_specs_foo_foo_xml` (the derive-source-name normalization of the same path). Invoke
   `kanon why repo-specs/foo/foo.xml` via subprocess; assert exit code non-zero and stderr lists
   both interpretations (XML path AND source name). Author a parallel case for URL + XML-path
   ambiguity using a `file://` URL whose pathname matches an XML manifest path. Run; confirm RED.
4. **TDD GREEN (integration):** Verify the unit-tier implementation suffices; re-run.
5. **TDD REFACTOR:** Factor the per-category matcher into three named helpers (`_match_by_url`,
   `_match_by_xml_path`, `_match_by_source_name`) returning a list of matched node references.
   The driver concatenates the lists. This keeps the SRP boundary clean for T3 (the Levenshtein
   suggester reads the same three universes when no match is found). No public-API changes.
6. **Docs:** Update the `why` section of `docs/cli-reference.md` to add the full matching-
   precedence list and the ambiguity-error description, mirroring spec Section 4.5 steps 2 and 3.
7. **Verify:** `uv run pytest tests/ -v && uv run ruff check src tests && uv run ruff format --check src tests && uv run mypy src && uv run bandit -r src -ll`.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
