# E13: kanon-claude-marketplaces audit + follow-up issue filing

## Status: in-queue

## Description

This epic delivers the sibling-repo audit scope (spec Section 9c) for the
`caylent/kanon-claude-marketplaces` repo. The repo is explicitly out of
scope for active migration in this spec; per Section 9c, a single backlog
task audits it against the same standards codified by E5 (the soft-spot
1-5 rules in spec Section 3.5 plus the trust-model rules in spec
Section 3.6) and files follow-up issues per violation. The audit does
NOT auto-fix; remediation is tracked separately by the
kanon-claude-marketplaces team via the filed issues.

One feature:

- **E13-F1 -- Audit kanon-claude-marketplaces and produce a report.**
  Runs the four kanon audit / validate commands shipped by E5 against
  the kanon-claude-marketplaces working tree, captures every finding,
  authors a comprehensive Markdown audit report committed to the repo's
  `audit-reports/` directory, and documents the recommended follow-up
  issues so the operator can copy-paste each one into the
  kanon-claude-marketplaces GitHub issue tracker.

Notes on shape:

- The target repo's layout differs from `caylent-private-kanon`. It has
  no `repo-specs/` directory and no `*-marketplace.xml` files; its
  content lives under `common/` and is described by per-plugin
  `.claude-plugin/marketplace.json` files plus a top-level
  `repo-config.json`. The audit task must run `kanon catalog audit`
  AND `kanon validate xml` / `kanon validate marketplace` /
  `kanon validate metadata` against the repo regardless; if any
  command finds no inputs to audit / validate it must report that as
  an INFO finding (not silently pass) so the report records the
  audit-coverage gap for follow-up.
- The audit task is **read-only against the target repo's source tree.**
  The only file it writes is the audit report itself.
- The audit task does NOT file GitHub issues itself. Per spec
  Section 3.6 (trust model) the kanon tooling and the orchestrator
  under devbench are provider-agnostic and never shell out to provider
  CLIs (`gh`, `glab`, etc.) or call provider HTTP APIs. The report
  includes ready-to-paste issue bodies so the operator files each one
  manually via the GitHub UI (or their own git client tooling).

Upstream dependencies:

- **E5 -- `kanon doctor` + `kanon catalog audit` + `kanon validate
  metadata` + standards codification.** The audit task invokes
  `kanon catalog audit`, `kanon validate xml`, `kanon validate
  marketplace`, and `kanon validate metadata`. All four must exist
  before E13 can run; E13's findings reference the soft-spot 1-5
  rules that E5-F2 codifies.

E13 is the LAST epic in this backlog; nothing in this backlog depends
on E13.
