# E4-F2: `kanon why` command

## Status: in-queue

## Description

Implement `kanon why <name-or-url>` (spec Section 4.5) as a new subcommand under
`src/kanon_cli/commands/`. The command reads `.kanon`, resolves the full dependency tree (from
`.kanon.lock` when present; otherwise live-resolves against the catalog, which requires a catalog
source), then walks every chain in the tree ending at the requested node and prints it.

Argument-to-tree-node matching follows the spec's precedence order (Section 4.5 step 2):

1. A `<project>` repo URL (most common case; canonicalized via `core/url.py::canonicalize_repo_url`
   from E1-F2).
2. A transitive XML manifest path (e.g., `repo-specs/git-connection/remote.xml`).
3. A top-level source name (a `KANON_SOURCE_<name>_*` key; matched via `derive_source_name()` from
   E2-F3 so both `foo_bar` and `Foo-Bar` resolve identically).

Ambiguity across categories is a hard error listing both interpretations (Section 4.5 step 3).
Not-found is a hard error with Levenshtein-distance-bounded closest-match suggestions (top 3, with
edit distance <= 3) drawn from the union of source names + project URLs + XML paths (Section 4.5
step 5).

Output: one line per chain, of the form `<top-level-source> -> <xml-manifest-path>@<resolved-sha>
-> ... -> <project>@<resolved-sha>`. With `--format json`: an array of chain objects; each chain a
list of `{kind, name, ref, sha, url}` nodes.

The feature decomposes into one story (`E4-F2-S1`) with four sequential tasks:

- **T1** -- Core chain-walker (subcommand registration, tree resolution from lockfile or live,
  default `text` format via `KANON_WHY_FORMAT`, chain enumeration + printing for the URL-match
  category).
- **T2** -- Ambiguity detection across the three matching categories.
- **T3** -- Levenshtein closest-match suggestion when the requested node is absent.
- **T4** -- `--format json` output.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.5 (all five behaviour steps) and
Section 7 (`KANON_WHY_FORMAT`, `--format`).
