# E12: Caylent-private-kanon Phase 2 -- delete the legacy `catalog/` directory tree

## Status: in-queue

## Target Repository

- **Repo:** `caylent/caylent-private-kanon`

## Description

Phase 2 of the caylent-private-kanon operational migration (spec Section 9b
Phase 2). Once every entry's author-facing metadata has been migrated into
its `*-marketplace.xml` `<catalog-metadata>` block by Phase 1 (E11), the
legacy `catalog/<name>/` per-entry directory tree is no longer the
source of truth and must be removed in its entirety.

Phase 2 is a single, mechanical, repo-wide deletion:

- `git rm -r catalog/` removes every tracked file under `catalog/` (today
  10 tracked files across 5 subdirectories: `devbench-backlog-builder/`,
  `history/`, `immutable-audit-trail/`, `kanon/`, `security-code-review/`,
  each containing a `.kanon` file plus a `README.md` or `kanon-readme.md`).
- Any internal tooling reference to `catalog/<name>/` paths anywhere in
  the repo (README docs, CI scripts, contributing guide, helper scripts)
  is removed in the same change so no orphan reference survives the delete.

Acceptance is binary and observable end-to-end:

1. `git ls-files catalog/` returns zero tracked files (the tree is gone
   from version control).
2. `kanon list --catalog-source <this-repo-at-HEAD>` still returns every
   expected entry (5 entries: `devbench-backlog-builder`, `history`,
   `immutable-audit-trail`, `security-code-review`, `builders-plugins`)
   after the delete -- proving the `kanon` CLI no longer needs the
   legacy directory tree to discover entries.
3. CI is green on the delete PR.

The kanon entry (`catalog/kanon/`) is in scope for this deletion: it is
a legacy `catalog/<name>/` directory like the others. It does NOT have
a Phase 1 sibling in E11 because the kanon entry was bundled-only (no
XML to migrate to); the bundled-catalog mirror inside the kanon wheel
is handled separately by E6-F2-S1-T1 (`caylent-solutions/kanon` repo).
After both E6-F2-S1-T1 and E12 land, no copy of `catalog/kanon/` exists
anywhere in the ecosystem.

E12 depends on every E11 task being `done`. The deletion cannot run
until every entry's metadata has been migrated into XML, because any
operator currently reading author-facing metadata from a `catalog/<name>/`
README must, post-deletion, find that content inside the entry's
`<catalog-metadata><description>` block.
