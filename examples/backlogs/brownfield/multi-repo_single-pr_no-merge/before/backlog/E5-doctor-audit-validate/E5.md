# E5: `kanon doctor` + `kanon catalog audit` + `kanon validate metadata` + standards codification

## Status: in-queue

## Description

This epic ships the three diagnostic and standards-enforcement commands that codify
the soft-spot rules defined in Section 3.5 of the spec and the workspace-health and
catalog-author checks defined in Sections 4.6 and 4.8:

- **`kanon doctor`** (Section 4.6) -- workspace health check. Cross-checks `.kanon`
  + `.kanon.lock` consistency via `kanon_hash`, detects hand-edits, orphaned lock
  entries, branch drift, dangling SHAs, completion-script staleness, and remote
  reachability. Reports the effective catalog source so an operator can spot
  `KANON_CATALOG_SOURCE` leakage from a shell profile. Adds
  `--refresh-completion-cache` and `--prune-cache` flags. Treats workspace concerns
  only; catalog-author checks live in `kanon catalog audit`.
- **`kanon catalog audit`** (Section 4.8) -- catalog-author / consumer-side audit.
  New `kanon catalog` subcommand group with `audit` as its first sub-subcommand.
  Accepts a directory path OR a `<url>@<ref>` catalog source. Runs the
  soft-spot 1-5 checks (metadata, source-name-derivation, entry-name-uniqueness,
  remote-url, tag-format) via `--check <subset>` (comma-separated or `all`).
  Detects legacy `catalog/<name>/` directory trees and emits a deprecation warning.
  `--strict` promotes warnings to errors.
- **`kanon validate metadata`** (Section 3.5) -- NEW sub-subcommand of the
  existing `kanon validate` command (which today has `xml` and `marketplace`).
  Runs the in-repo subset of soft-spot checks (1, 2, 3) for catalog authors
  editing their manifest repo locally; does NOT clone (no network).

E5 codifies the "standards" half of the standards-codification-and-tightening
goal: every soft-spot rule from Section 3.5 has a deterministic, automated
check that catalog authors and consumers can run before they ship or adopt a
manifest repo. The workspace-health half (`kanon doctor`) gives operators
a single command that reveals every reason the next `kanon install` might fail.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Sections 3.5, 3.6,
4.6, 4.8.

Upstream dependencies:

- E1 -- shared `--catalog-source` arg, URL canonicalization, resolver semantics.
- E2 -- `parse_catalog_metadata`, source-name derivation, entry-name parsing.
- E3 -- lockfile schema + `kanon_hash`, lockfile I/O, install state machine.
