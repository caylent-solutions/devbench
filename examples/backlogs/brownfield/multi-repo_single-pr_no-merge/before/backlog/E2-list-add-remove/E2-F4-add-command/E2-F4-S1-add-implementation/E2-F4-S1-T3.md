## Description

Add the loud-error path to `kanon add` for the default-spec case when the
manifest repo has zero PEP 440-valid tags. Per spec Section 4.2 step 4:

> Otherwise default to the highest PEP 440-valid git tag on the manifest
> repo (queried via `git ls-remote --tags`, parsed by
> `packaging.version.Version`). If zero PEP 440-valid tags exist, hard
> error: "manifest repo has no PEP 440-valid tags; pin to a branch or SHA
> explicitly (e.g., 'kanon add foo@main') or ask the catalog author to
> publish a release tag."

Path coverage clarification:

- The case "manifest repo HAS tags but NONE parse as PEP 440" is handled
  by E1-F1-S1-T2's loud error inside
  `_resolve_constraint_from_tags`. That path fires when the operator
  supplies an explicit `@<spec>` constraint and the constraint resolution
  finds zero candidates.
- This task adds the DEFAULT-spec path's loud error, which fires BEFORE
  any constraint resolution: the operator did not supply `@<spec>`, and
  the bare `git ls-remote --tags` query returns either zero tags total OR
  zero tags whose last path component parses as `packaging.version.Version`.

New fixture under `tests/fixtures/catalogs/zero-pep440-tags/`:

- A self-contained git repository tree (committed via `git init` +
  `git add` + `git commit` in a `conftest.py` helper, or shipped as a
  pre-built bare clone) with:
  - At least one `*-marketplace.xml` in `repo-specs/` so the entry index
    is non-empty.
  - Either zero tags, OR tags whose last path components are
    non-PEP-440 (e.g., `release-2024`, `ops-marker`).
- A scenarios-table test ensures both subcases (zero tags vs zero
  PEP-440 tags) exercise the same error path.

Integration test:

- Invokes `kanon add <entry>` (no `@<spec>`) against the new fixture and
  asserts:
  - Exit code non-zero.
  - Stderr contains the spec-verbatim error string.
  - The destination `.kanon` is unchanged (or absent if it did not
    pre-exist).
