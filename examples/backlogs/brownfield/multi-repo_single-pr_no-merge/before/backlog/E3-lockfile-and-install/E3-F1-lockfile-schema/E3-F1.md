# E3-F1: Lockfile schema and TOML I/O

## Status: in-queue

## Description

Introduces the `.kanon.lock` TOML file format and the reader/writer module
`src/kanon_cli/core/lockfile.py`. This feature owns:

- **Schema v1 definition** (spec Section 5): top-level keys
  (`schema_version`, `generated_at`, `generator`, `kanon_hash`); the
  `[catalog]` block (manifest-source URL + revision + resolved ref / SHA);
  the `[[sources]]` array of top-level sources; nested `[[sources.includes]]`
  representing transitive `<include>` chains (depth unbounded); and
  `[[sources.projects]]` rows carrying `canonical_url`.
- **Validation rules** (spec Section 5 bullets): `resolved_sha` is 40 or 64
  hex characters; `revision_spec` parses as PEP 440 OR matches `refs/...` OR
  is a branch name matching `[a-zA-Z0-9_./+-]+`; `canonical_url` on every
  project row equals `canonicalize_repo_url(url)`; `path` and `path_in_repo`
  reject embedded NUL / newline / tab characters.
- **Atomic writer** using a write-temp-then-rename pattern in the same
  directory as the target lockfile, so a SIGTERM mid-write leaves either the
  prior lockfile content or the new content, never a truncated file.
- **Schema migration policy** (spec Section 5.2): forward-incompatible reads
  (older kanon trying to parse a newer schema) raise a structured error
  naming the schema number and the upgrade instruction; backward-compatible
  reads (newer kanon parsing an older schema) run a per-version upgrader.
- A new constant `KANON_LOCK_FILE` env-var name added to
  `src/kanon_cli/constants.py` for use by E3-F3 commands.

This feature does not branch on lockfile state (that is E3-F3) and does not
compute `kanon_hash` (that is E3-F2). It only handles the file-format
contract: parse, validate, write, migrate.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 5
(Lockfile format and validation rules) and Section 5.2 (Schema migration
policy).
