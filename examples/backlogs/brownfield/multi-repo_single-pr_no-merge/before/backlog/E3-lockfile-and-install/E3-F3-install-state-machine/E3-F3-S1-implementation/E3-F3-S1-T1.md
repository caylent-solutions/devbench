# E3-F3-S1-T1: Lockfile state-matrix branching in `kanon install`

## Status: in-queue

## Target Repository

- **Repo:** `caylent-solutions/kanon`
- **Branch:** `backlog/e3-f3-s1-t1`

## Description

Modify `src/kanon_cli/core/install.py::install` to read the lockfile (when
present), compare `kanon_hash(.kanon)` to the lockfile's `kanon_hash` field,
compare the lockfile's `[catalog].source` to the CLI/env catalog source, and
branch on the five-row state matrix from spec Section 4.7:

| State | Behaviour |
|---|---|
| `.kanon` exists, `.kanon.lock` absent | Resolve every transitive version fresh; install; write `.kanon.lock` capturing every resolved SHA + the catalog source + the `kanon_hash`; emit info-line `"lockfile rebuilt from .kanon (N sources, M projects)"`. |
| `.kanon` exists, `.kanon.lock` exists, both consistent (matching `kanon_hash`) | Install EXACTLY the SHAs in the lockfile; do NOT re-resolve; ignore newer tags; emit info-line `"installing from lockfile (N sources, M projects)"`. Catalog source MAY be read from the lockfile's `[catalog].source` when no CLI/env source is set. |
| `.kanon` modified (hash mismatch) | Hard error. Remediation: `kanon install --refresh-lock` or `--refresh-lock-source <name>`. |
| `.kanon.lock` references a SHA no longer reachable on remote | Hard error. Remediation: `kanon install --refresh-lock-source <name>` for the affected source. |
| `.kanon.lock` records a different `[catalog].source` than the CLI/env source (when CLI/env is set) | Hard error. The lockfile is authoritative; remediation is `--refresh-lock` (operator changed catalogs intentionally). |

Implementation surface:

- Add `read_lockfile_if_present(path: Path) -> Lockfile | None` helper in
  `core/install.py` (or extract to `core/lockfile.py` if it fits the SRP
  there; T1's lockfile module is the natural home). Returns `None` for an
  absent path; raises through for any other error.
- Compute `kanon_hash(.kanon)` once per install invocation; pass the value
  through to the lockfile-write path so the new lockfile records the
  hash that produced it.
- Add the catalog-source resolution rule: precedence is CLI flag, then
  `KANON_CATALOG_SOURCE` env var, then `lockfile.[catalog].source` (only on
  the consistent state; never on refresh paths). If none of these is set,
  raise `MissingCatalogSourceError` with the spec's standard message.
- Define the new state-branch info-line emit function
  `_emit_install_state(state: InstallState, sources: int, projects: int)`
  that prints the spec's exact info-line text for the matching state.
- Define the new exception classes in `core/install.py`:
  `KanonHashMismatchError`, `LockfileUnreachableShaError`,
  `CatalogSourceMismatchError`. Each carries the standard error-shape
  payload (one-line summary, context, remediation line).

This task does NOT implement the four state-rows that are owned by sibling
tasks: branch-drift, transitive-conflict (T5), orphan-lock-entry (T4),
include-cycle/diamond (T6), HTTPS-enforcement (T8). T1 ships the
foundation; the sibling tasks layer their behaviour on top of the
branching framework T1 introduces.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.7 (the
state matrix), Section 4.7.1 (engine contract), and Section 4 header
(catalog-source resolution precedence with lockfile fallback).

### Approach

1. **TDD RED (unit):** Author `tests/unit/test_install_state_matrix.py`
   parametrising the five state rows. Each test mocks out the resolver and
   the symlink aggregator (existing helpers in `core/install.py` already
   support mocking via dependency injection), constructs a synthetic
   `.kanon` plus optional `.kanon.lock` on `tmp_path`, and asserts the
   correct branch is taken: which info-line is emitted, whether the
   lockfile is rewritten, whether a hard error is raised with the expected
   exception class and message.
2. **TDD RED (integration):** Author
   `tests/integration/test_install_lockfile_replay.py` exercising the
   `lockfile-consistent` row end-to-end: build a fixture git repo with a
   tagged release, run `kanon install` to produce a baseline lockfile,
   modify the remote (add a newer tag), run `kanon install` again, assert
   the lockfile is unchanged AND the installed SHA matches the original
   tag (the newer tag is ignored).
3. **TDD GREEN:** Add the lockfile-reading branch to
   `core/install.py::install`. The function's signature extends with a
   new keyword argument `lock_file_path: Path | None = None` (the resolved
   default is provided by T7; T1 accepts whatever is passed).
4. **TDD GREEN (catalog-source resolution):** Extract a helper
   `_resolve_catalog_source(cli_arg, env_value, lockfile_catalog_source,
   install_state)` that implements the precedence rule and the
   state-dependent lockfile fallback. The helper returns the canonical
   `<url>@<ref>` string or raises `MissingCatalogSourceError`.
5. **TDD GREEN (error classes):** Define `KanonHashMismatchError`,
   `LockfileUnreachableShaError`, and `CatalogSourceMismatchError` as
   subclasses of a new base `InstallError(Exception)`. Each error class
   accepts a structured payload (summary, context, remediation) and
   renders via `str(err)` to the spec's standard three-line shape.
6. **TDD GREEN (info-line emit):** Implement `_emit_install_state` to
   print the spec's verbatim info-lines to stdout (info-level, not
   stderr). The info-line text is parametrised on `(state, sources_count,
   projects_count)`.
7. **TDD REFACTOR:** If existing helpers in `core/install.py` overlap with
   the new branching code, extract a private `_classify_install_state(.kanon_path,
   lockfile_path)` function that returns an `InstallState` enum, so the
   downstream branch is a tidy `match state:` block.
8. **Docs:** Update `docs/architecture.md` (NEW per spec Section 4.7.1)
   with the install state-matrix diagram and the new error-class table.
   Update `docs/lockfile.md` with the cross-link from each lockfile field
   to the state branch that reads it.
9. **Verify:** Full suite.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
