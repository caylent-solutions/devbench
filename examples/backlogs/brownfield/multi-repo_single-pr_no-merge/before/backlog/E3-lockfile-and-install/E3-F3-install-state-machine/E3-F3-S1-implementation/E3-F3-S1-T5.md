# E3-F3-S1-T5: Canonical-URL conflict detection at the `<project>` level

## Status: in-queue

## Target Repository

- **Repo:** `caylent-solutions/kanon`
- **Branch:** `backlog/e3-f3-s1-t5`

## Description

Today's `kanon install` detects symlink-name conflicts when two sources
produce the same package name in `.packages/`. This task extends conflict
detection ONE level deeper: when two `<project>` entries (potentially from
different XML manifests across different top-level sources) resolve to the
same canonicalized URL but different SHAs, `kanon install` raises a hard
error. Spec Section 4.7 "Transitive conflict" row:

> Two `<project>` entries point at same canonicalized repo URL, different
> SHAs -> Hard error. List both source paths AND the canonicalization
> that produced the match.

The conflict detector runs after all transitive resolution completes (every
`<project>` row has been resolved to a concrete SHA) and before the lockfile
is written. It uses `canonicalize_repo_url` (E1-F2-S1-T1) to normalise each
`<project>` URL before comparison; the comparison key is the canonical
URL string.

The error message MUST include:

- Both source paths in the form `<top-level-source-name>/<xml-path>` so the
  operator can trace each conflicting `<project>` back to the manifest
  that declared it.
- The canonicalization that produced the match. For example, if one
  `<project>` URL is `git@github.com:org/repo.git` and another is
  `https://github.com/org/repo`, the error includes a line like
  `"both URLs canonicalize to: https://github.com/org/repo"`.
- The two different SHAs.

Implementation surface:

- Add `_detect_canonical_url_conflicts(all_projects: list[ResolvedProject]) ->
  list[CanonicalUrlConflictReport]` helper in `core/install.py`. Each
  report carries the canonical URL, the list of `(source_path,
  xml_path, raw_url, resolved_sha)` tuples that share it, AND fires only
  when two or more of those tuples have differing `resolved_sha` values.
  Same SHA across multiple sources is allowed (it is a benign diamond).
- Add `CanonicalUrlConflictError(InstallError)` exception class. The
  error renders one report per line in the standard three-line shape.
- Wire the detector into both the `lockfile-absent` path (fresh
  resolution) and the `lockfile-consistent` path (replay path; the
  conflict was already in the lockfile but the operator may have
  switched to a workspace where the conflict surfaces). On the
  consistent path, the detector runs against the lockfile contents
  rather than fresh resolution outputs.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.7
"Transitive conflict" row, plus Section 4.5 (where the same canonical-URL
matching is used for `kanon why`).

### Approach

   with parametrised cases covering: (a) two `<project>` rows with
   different raw URLs but same canonical URL and same SHA -> allowed; (b)

   error listing all three. RED phase confirms tests fail against an
   absent detector.

   `tests/integration/test_install_conflict_url_normalization.py` with a
   fixture pair: one manifest declares
   `git@gitserver:org/example-package.git@1.0.0` and another declares
   `https://gitserver/org/example-package.git@2.0.0`; both canonicalize
   to `https://gitserver/org/example-package` but pin different tags ->

   `CanonicalUrlConflictError` and the error message includes both the
   ssh and https raw forms plus the canonical form.

   removing one source or aligning REVISION values across sources.").

6. **Docs:** Update `docs/lockfile.md` and `docs/troubleshooting.md`
   (existing) with the canonical-URL conflict scenario and recovery
   guidance.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. 8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
