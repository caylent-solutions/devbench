## Description

Implement the output sanitizer from Section 11.3 "Output
sanitization" paragraph and Section 3.6 trust model ("Completion
candidates are shell-escaped").

The sanitizer rejects entries containing:

- ASCII newline (`\n`, 0x0a) or carriage return (`\r`, 0x0d).
- ASCII NUL (`\x00`).
- Shell metacharacters from a closed set defined in
  `src/kanon_cli/constants.py::SHELL_METACHARS = "|&;<>(){}$`\\\"'"` plus
  any character below 0x20 (control chars).

API in `src/kanon_cli/completions/sanitize.py`:

```python
class SanitizationResult(NamedTuple):
    kept: list[str]
    dropped: list[tuple[str, str]]   # (entry, rejection_reason)

def sanitize_entries(entries: Iterable[str], completer_name: str) -> SanitizationResult: ...
```

Behavior:

- For each entry: walk character-by-character; on first
  forbidden character, drop the entry and record the rejection
  reason (e.g., `"contains newline"`, `"contains NUL"`,
  `"contains shell metacharacter '|'"`, `"contains control char 0x07"`).
- Return the kept list (preserving original order) and the dropped
  list.
- The caller (`cache.write_entries`) writes only the kept list to
  the cache file AND calls `log_completion_error` once per dropped
  entry (`log_completion_error(completer_name, SanitizationError(reason))`)
  via a new `SanitizationError` exception class also in
  `sanitize.py`.

`cache.write_entries` is updated to call `sanitize_entries`
INTERNALLY before writing; the public API of `write_entries` is
unchanged so completers continue to call it without changes. The
stub sanitizer that T1 shipped is replaced by the real
implementation.

Spec source: spec Section 11.3 "Output sanitization" paragraph
("rejects entries containing newlines, NULs, or shell metacharacters
that would break the completion protocol. Rejected entries are
dropped from stdout AND logged to `completion-errors.log`."),
Section 3.6 trust model.

### Approach

1. **TDD RED:** Author `tests/unit/test_completion_sanitization.py`
   with parametrized cases for: clean entries pass through;
   entry with newline -> dropped with reason; entry with NUL ->
   dropped; entry with each shell metacharacter (parametrized
   over `SHELL_METACHARS`) -> dropped; entry with bell (0x07) ->
   dropped (control char); mixed list -> kept entries preserved
   in order, dropped entries collected; empty input -> empty
   output; SanitizationError raised carries the reason and the
   original entry.
2. **TDD GREEN:** Implement
   `src/kanon_cli/completions/sanitize.py` with
   `sanitize_entries`, `SanitizationError`, and `SanitizationResult`.
   Wire it into `cache.write_entries` so the public API is
   unchanged but only sanitized entries reach disk. Move
   `SHELL_METACHARS` into `src/kanon_cli/constants.py`.
3. **TDD REFACTOR:** Ensure the sanitizer body uses a single
   pass over the entry's characters (O(n) per entry, not O(n*k)
   for k forbidden classes). Document the perf shape in the
   docstring qualitatively (no quantitative claims).
4. **Docs:** Update `docs/shell-completion.md` "Cache layout"
   section with a "Sanitization" subsection naming the rejected
   character classes.
5. **Verify:** Run the full suite locally:
   `uv run pytest tests/ -v && uv run ruff check src tests && uv run ruff format --check src tests && uv run mypy src && uv run bandit -r src -ll`.

2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.

Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
