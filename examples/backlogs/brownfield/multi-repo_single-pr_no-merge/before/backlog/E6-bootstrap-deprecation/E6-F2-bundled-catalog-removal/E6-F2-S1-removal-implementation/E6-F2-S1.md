# E6-F2-S1: Bundled catalog removal and resolver fallback cleanup

## Status: in-queue

## Description

Story scope: remove the bundled `src/kanon_cli/catalog/` directory
tree from the kanon wheel and remove the resolver fallback that
silently returned it. The story is decomposed into two tasks:

1. **T1 -- Wheel removal + repo guard**: `git rm -r
   src/kanon_cli/catalog/`; verify `pyproject.toml`'s
   `[tool.hatch.build.targets.wheel] packages` / `include` lists
   do not reintroduce the dir via globs; add a wheel-layout test
   that builds the wheel and asserts the archive does not contain
   any `catalog/` member; add an integration test that asserts
   `importlib.resources.files("kanon_cli")` does NOT expose a
   `catalog/` subpath at runtime; add a gitignore guard or CI check
   that fails the build if `src/kanon_cli/catalog/` reappears in
   a future commit.
2. **T2 -- Resolver fallback removal**: modify
   `src/kanon_cli/core/catalog.py::resolve_catalog_dir` so when
   `--catalog-source` is None AND `KANON_CATALOG_SOURCE` is unset,
   the function raises the canonical missing-catalog error from
   spec Section 4 (verbatim text) instead of returning the bundled
   directory. Delete the `_get_bundled_catalog_dir()` helper
   function (no consumers remain). Update every test exercising the
   today's bundled-fallback path to assert the new hard-error
   behaviour instead.

T2 depends on T1 because removing the resolver fallback while the
bundled tree is still on disk would mean the resolver hard-errors
even though the bundled tree is present -- a confusing intermediate
state. T1 removes the tree first, T2 removes the code path that
referenced it.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4
header (third-tier fallback removed) + Section 0.3 (bundled
deletion) + Section 13 decision 19 (no default manifest repo).
