# E1-F4-S1-T2: Add global flags `--quiet`, `--verbose`, `--no-color` to shared `core/cli_args.py`

## Description

Extend the shared CLI-args module `src/kanon_cli/core/cli_args.py`
(introduced by E1-F4-S1-T1) with a factory for the spec-required global
flags `--quiet`, `--verbose`, and `--no-color`, and plumb them through
the root argparse parser in `src/kanon_cli/cli.py` so every subcommand
inherits the parsed values via argparse's natural namespace propagation.

The new module-level factory:

```python
def add_global_flags(parser: argparse.ArgumentParser) -> None:
    """Add the global flags --quiet, --verbose, --no-color to the given parser.

    --quiet / --verbose are MUTUALLY EXCLUSIVE; passing both raises an
    argparse error immediately (fail-fast per spec Section 7).

    --no-color disables ANSI color regardless of TTY / NO_COLOR env var
    (precedence: --no-color > NO_COLOR env var > TTY auto-detect).
    """
```

And the companion runtime helper:

```python
def _apply_global_flags(args: argparse.Namespace) -> None:
    """Translate parsed args into runtime state.

    - Sets the root logger level: WARNING if args.quiet, DEBUG if
      args.verbose, INFO otherwise.
    - Sets the module-level color-suppression state used by every
      formatter helper (constants._NO_COLOR_ACTIVE) when --no-color is
      set OR when the NO_COLOR env var is non-empty. Precedence:
      --no-color flag > NO_COLOR env var > TTY auto-detect.

    Idempotent: calling twice with the same args produces the same
    state. Fails fast (raises ValueError) if both args.quiet and
    args.verbose are True (defence-in-depth; argparse's mutually
    exclusive group should prevent this case ever reaching the
    helper).
    """
```

Spec mapping:
- `spec/kanon-list-add-lock-features-spec.md` Section 7 lines 735-746:
  `--quiet` / `--verbose` mutual exclusion; `--no-color` precedence over
  `NO_COLOR` env var; deterministic color decision (no prompting).
- Section 7 line 808 (global flag table row): `--quiet` / `--verbose`
  global, mutually exclusive; `--no-color` alternative to `NO_COLOR`.
- Section 11.2 line 1083: completion entry for `--quiet`, `--verbose`,
  `--no-color` as static no-value flags on _all_ commands.
- Section 12 item 25 (lines 934-935): functional test for both flags
  passed together raising a hard error; `NO_COLOR=1` suppresses color
  even on TTY; `--no-color` wins.
- Section 14 lines 1349-1350: `kanon --help` output documents the
  Global options block listing all three flags.

### Integration design

Two competing integration paths were considered. They are documented
here so the trade-off is auditable.

**Path A (rejected): re-wire every command parser task.**
Modify the per-command tasks in E2/E3/E4/E5/E7 to call
`add_global_flags(parser)` on their subcommand parser. This requires
editing 10+ already-authored tasks (E2-F2-S1-T1, E2-F4-S1-T1,
E2-F5-S1-T1, E3-F3-S1-T1, E4-F1-S1-T1, E4-F2-S1-T1, E5-F1-S1-T1,
E5-F2-S1-T1, E5-F3-S1-T1, E7-F1-S1-T1) and creates an artificial
dependency cycle.

**Path B (chosen): wire at the root parser only.**
Call `add_global_flags(root_parser)` once on the top-level argparse
parser in `src/kanon_cli/cli.py`. argparse propagates the parsed
namespace to every subcommand by design, so `args.quiet`,
`args.verbose`, and `args.no_color` are present on every subcommand's
`args` without per-subcommand wiring. Call `_apply_global_flags(args)`
early in `main()` before dispatching to subcommand handlers; the
side-effects (logger level, color state) then apply uniformly.

The per-command `--no-color` definitions that already exist in some
downstream command tasks become redundant after this lands. They are
NOT removed in this Task (avoids retroactive churn across already-
authored tasks); argparse will accept the duplicate definition only if
the subparser uses a fresh parser, and the global namespace wins for
the top-level flag. Downstream tasks may opt to delete their inline
definitions in a follow-up cleanup epic.

This Task ships:
1. The `add_global_flags` factory in `core/cli_args.py`.
2. The `_apply_global_flags` runtime helper in `core/cli_args.py`.
3. The root-parser wire-up in `cli.py` plus an `_apply_global_flags`
   call early in `main()`.
4. The new constants (`NO_COLOR_ENV`, `_NO_COLOR_ACTIVE`) in
   `constants.py`.
5. Source-test-atomic unit-test files for every new/modified source
   file per `devbench/docs/source-test-atomicity.md`.
6. Documentation in `docs/configuration.md` describing the global
   flags and the precedence rules.

### Approach

1. **TDD RED (factory unit tests):** Extend `tests/unit/test_cli_args.py`
   with parametrised cases for `add_global_flags`:
   - Calling `add_global_flags(parser)` registers exactly three

   - `parser.parse_args(["--quiet", "--verbose"])` exits with non-zero
     and an argparse error message naming "not allowed with" both
     flags (mutual exclusion).
   - `parser.parse_args(["--quiet"])` sets `args.quiet is True` and
     `args.verbose is False`.
   - `parser.parse_args(["--verbose"])` sets `args.verbose is True`
     and `args.quiet is False`.
   - `parser.parse_args(["--no-color"])` sets `args.no_color is True`.
   - `parser.parse_args([])` leaves all three flags `False`.
   Run `uv run pytest tests/unit/test_cli_args.py -v`; cases FAIL
   because `add_global_flags` does not yet exist.
2. **TDD RED (apply-helper unit tests):** Extend
   `tests/unit/test_cli_args.py` with parametrised cases for
   `_apply_global_flags`:
   - With `args.quiet=True, args.verbose=False`, the root logger's
     effective level is `logging.WARNING`.
   - With `args.verbose=True, args.quiet=False`, the root logger's
     effective level is `logging.DEBUG`.
   - With both `False`, the root logger's effective level is
     `logging.INFO`.
   - With `args.no_color=True`, `constants._NO_COLOR_ACTIVE is True`.
   - With `args.no_color=False` and env `NO_COLOR=` (empty),
     `constants._NO_COLOR_ACTIVE is False`.
   - With `args.no_color=False` and env `NO_COLOR=1` (non-empty),
     `constants._NO_COLOR_ACTIVE is True`.
   - With `args.no_color=True` and env `NO_COLOR=` (empty),
     `constants._NO_COLOR_ACTIVE is True` (flag wins).
   - With both `args.quiet=True` AND `args.verbose=True` (defence-in-
     depth: bypassing argparse), raises `ValueError` with a message
     naming both flags.

     the same end-state.

### Code Standards

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.

#### Security Rules

- **NO eval() / exec()** -- Never execute dynamic code from external input.
- **NO PROVIDER-SPECIFIC API CALLS** -- Per spec Section 3.6, kanon NEVER calls provider HTTP APIs (`api.github.com`, `gitlab.com/api`, etc.) and NEVER shells out to provider CLIs (`gh`, `glab`, `bb`, `tea`, `aws codecommit`, `az repos`). Every git interaction is via the `git` binary only.

#### Error Handling Contract

- Include context in error messages: file paths, variable names, expected vs actual values, the operator's likely next step.
- Never catch and discard exceptions.
- Never call `sys.exit()` from library code; only from CLI command handlers in `src/kanon_cli/commands/` or `src/kanon_cli/cli.py`.
- Error messages follow the standard shape per spec Section 4: `ERROR: <one-line summary>` then optional context lines (wrapped at 80 cols), then a remediation line when applicable.
