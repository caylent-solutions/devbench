# E2-F4: `kanon add` command

## Status: in-queue

## Description

Implement the new top-level `kanon add` subcommand per spec Section 4.2.
The command accepts one or more catalog entry references in the form
`<name>[@<spec>]` and writes the matching
`KANON_SOURCE_<source_name>_{URL,REVISION,PATH}` triples to a `.kanon`
file (creating the file with the standard header if absent).

The feature ships as three sequential tasks in a single story:

- **T1** introduces the command shell, the core triple-writing path (reads
  each requested entry's `<catalog-metadata>` via the E2-F1 helper,
  derives the source name via the E2-F3 helper, constructs the three
  triples directly from the XML metadata with NO pre-baked template
  lookup), registers the subcommand on the top-level argparse parser,
  and creates the destination file with the standard header
  (`GITBASE`, `CLAUDE_MARKETPLACES_DIR`, `KANON_MARKETPLACE_INSTALL`) if
  it does not exist.
- **T2** adds `--dry-run` (prints the diff with no file change),
  `--force` (overrides collision detection), and the collision-detection
  pre-flight checks (against both the requested set AND existing
  source-name blocks in the destination file).
- **T3** adds the loud error for the default-spec path when the manifest
  repo has zero PEP 440-valid tags. (The "tags-exist-but-none-parse-as-
  PEP-440" case is handled by E1-F1-S1-T2's loud error inside
  `_resolve_constraint_from_tags`; this task handles the
  "manifest-repo-has-no-tags-at-all" case for the bare-default-spec path.)
  A new git fixture under `tests/fixtures/catalogs/zero-pep440-tags/`
  exercises the error.

Spec source: spec Section 4.2.
