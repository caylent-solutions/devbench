## Description

Implement the `entry-name-uniqueness` check inside
`src/kanon_cli/commands/catalog.py` per spec Section 3.5 soft-spot rule 3.

`<catalog-metadata><name>` MUST be unique across every
`repo-specs/**/*-marketplace.xml` file in the manifest repo. The check
function (`_check_entry_name_uniqueness(target_path)`) builds a mapping
from `entry-name -> list[xml_path]` while iterating, then emits one
ERROR finding per collided name listing every offending XML path.

Edge cases:

- An entry name that appears only once produces no finding.
- An entry name that appears in N > 1 files produces ONE finding (not
  N), listing all N paths.
- An XML file that fails metadata parsing (missing `<name>` entirely)
  does NOT contribute to uniqueness collisions. Its missing-name error
  is the `metadata` check's responsibility (T2). The uniqueness check
  ignores files with no parseable entry name to avoid duplicating
  errors.
- Names are compared case-sensitively. `Foo` and `foo` are distinct
  here; T3's source-name-derivation check emits a separate warning that
  both normalise to the same source name (which IS a real install-time
  collision risk). Authors who want case-insensitive uniqueness can
  read T3's warning.

Register the check in the registry T1 created under name
`entry-name-uniqueness`.

Source-test atomicity: this task modifies `catalog.py` (existing after
T1) and adds new tests. Fixture:
`tests/fixtures/catalog/broken-soft-spot-3/` with two pairs of colliding
entries demonstrating the multi-path error message.

Spec source: spec Section 3.5 soft-spot rule 3; Section 4.8 (`--check
entry-name-uniqueness`).
