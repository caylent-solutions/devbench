# E10-F2-S1-T2: CI guard no-catalog-dir.yml -- block new catalog/<name>/ paths

## Status: in-queue

## Target Repository

- **Repo:** `caylent/caylent-private-kanon`
- **Branch:** `backlog/e10-f2-s1-t2`

## Description

Create the GitHub Actions workflow `.github/workflows/no-catalog-dir.yml`
in the `caylent/caylent-private-kanon` repo. The workflow runs on every
PR (`pull_request`) and fails the build if the PR introduces any new
path matching `^catalog/[^/]+/` -- the legacy per-entry directory
shape that is being deprecated and will be deleted in E12 Phase 2 (spec
Section 9b).

The guard's behaviour envelope is documented in spec Section 9a CI
bullet 4:

> Before Phase 2, the guard tolerates the existing tree but errors on
> NEW entries.

After E12 Phase 2 lands and deletes the entire `catalog/` tree, this
guard prevents reintroduction by the same mechanism (any new
`catalog/<name>/` path in a PR diff is rejected).

### Implementation

1. Trigger: `on: pull_request` (no push-to-main trigger; the guard is
   pre-merge by design -- main is what the PR is diffed against).
2. Job `no-catalog-dir` on `ubuntu-latest`:
   - `actions/checkout@<pinned>` with `fetch-depth: 0` so
     `origin/main` is reachable.
   - Resolve the base ref. For a `pull_request` event, the base ref
     is `${{ github.event.pull_request.base.ref }}`; the workflow
     fetches and diffs against `origin/${{ github.event.pull_request.base.ref }}`.
   - Run, in a single `run: shell: bash` step with `set -euo pipefail`:
     ```bash
     base_ref="${{ github.event.pull_request.base.ref }}"
     git fetch origin "${base_ref}" --depth=0
     added=$(git diff --name-only --diff-filter=A "origin/${base_ref}..HEAD" \
       | grep -E '^catalog/[^/]+/' || true)
     if [ -n "${added}" ]; then
       printf 'ERROR: this PR introduces new catalog/<name>/ paths:\n%s\n' "${added}" >&2
       printf 'Remediation: add a new *-marketplace.xml under repo-specs/ instead. See docs/contributing.md.\n' >&2
       exit 1
     fi
     ```
   - Critical detail: the regex MUST be `^catalog/[^/]+/` (note the
     trailing slash) so the guard fires only on per-entry
     SUBDIRECTORIES under `catalog/`, not on a hypothetical
     non-directory file directly inside `catalog/` (which is a
     different kind of pollution and out of scope for this guard).
   - `--diff-filter=A` restricts to ADDED paths only; renames into
     the legacy shape (`R`) are also a violation -- handle by
     adjusting the filter to `--diff-filter=AR` so a `git mv
     repo-specs/foo-marketplace.xml catalog/foo/foo-marketplace.xml`
     is caught.

### Behaviour during the deprecation window

Before E12 Phase 2 lands, the repo still contains the legacy `catalog/`
tree on `main`. The guard's design is "delta-only" -- it inspects the
PR's added/renamed paths, not the repo state at HEAD -- so the
existing tree on main is invisible to this guard and produces zero
false positives. Once E12 Phase 2 deletes the entire `catalog/` tree
on main, this guard's behaviour is identical: any reintroduction
appears as an ADD relative to the now-empty base, and the guard fires.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.

#### Security Rules
