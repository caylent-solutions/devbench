## Description

Layer the schema migration policy on top of T1's `read_lockfile`. After
this task, the read path behaves as follows when it encounters a
`schema_version` other than the current shipping schema (v1):

- **Forward-incompatible read** (`schema_version > current_schema`): raise
  `LockfileSchemaError` with the exact message `"lockfile schema vN
  written by newer kanon; upgrade kanon-cli."` (where `N` is the offending
  version number). The error is fatal; there is no autodetection of a
  newer wire format. This rule supersedes T1's stub behaviour for unknown
  schema versions.
- **Backward-compatible read** (`schema_version < current_schema`): look
  up the per-version upgrader in a registry keyed by `(from_version,
  to_version)`. If a chain of upgraders exists that transforms the data
  from `from_version` to `current_schema`, run each upgrader in sequence
  and return the upgraded `Lockfile`. If no chain exists, raise
  `LockfileSchemaError` with message `"no upgrade path from lockfile
  schema vN to v<current>; this is a kanon bug; please report."` (the
  "kanon bug" framing is correct because the spec mandates an explicit
  per-version upgrade path; missing one is a packaging defect).
- **Current-schema read** (`schema_version == current_schema`): unchanged
  from T1.

The upgrader registry is shipped empty (v1 is the only schema today), but
the dispatch infrastructure exists so future v2 ships with a single
registry entry rather than a refactor. The registry MUST have at least one
test case to validate the dispatch wiring: T2's test suite installs a
fake v0-to-v1 upgrader at module import time, parses a v0 fixture file,
asserts the result is the upgraded v1 `Lockfile`, and removes the fake
upgrader at teardown.

`kanon install --refresh-lock` is the operator's explicit lever for
rewriting a lockfile at the current schema; it ships as part of E3-F3-S1-T2.
This task does not modify the install command path; it only handles the
read-time migration policy.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 5.2
(Lockfile schema migration policy).

### Approach

1. **TDD RED:** Extend `tests/unit/test_lockfile_schema_migration.py` (NEW)
   with parametrised cases for: forward-incompatible read (schema 2, 99);
   missing-upgrader backward-incompatible read (schema 0 with no registered
   upgrader); successful backward-compatible read (schema 0 with a test-only
   v0-to-v1 upgrader installed). RED phase confirms the forward-incompat
   path already passes (T1 stub) but the backward-compat dispatch fails.
2. **TDD GREEN:** Add `CURRENT_SCHEMA_VERSION = 1` to
   `src/kanon_cli/core/lockfile.py`. Add a `_UPGRADERS: dict[tuple[int, int],
   Callable[[dict], dict]]` registry. Add `_dispatch_migration(data: dict)
   -> dict` that walks the `(from_version, to_version)` chain to reach
   `CURRENT_SCHEMA_VERSION`. Modify `read_lockfile` to call
   `_dispatch_migration` before dataclass hydration when
   `data["schema_version"] != CURRENT_SCHEMA_VERSION`.
3. **TDD GREEN (forward-incompat):** Refine the existing
   `LockfileSchemaError` message in `read_lockfile` to the spec's exact
   text: `"lockfile schema v<N> written by newer kanon; upgrade
   kanon-cli."` (note the trailing period; mirrors spec verbatim).
4. **TDD GREEN (missing-upgrader):** When `_dispatch_migration` cannot
   find a chain, raise `LockfileSchemaError` with the exact text `"no
   upgrade path from lockfile schema v<N> to v<current>; this is a kanon
   bug; please report."`.
5. **TDD REFACTOR:** Extract the upgrader-registration helper as a
   public-but-private-by-convention API
   (`_register_upgrader(from_version: int, to_version: int, fn)`) so tests
   can register fakes without touching the registry dict directly.
6. **Docs:** Update `docs/lockfile.md` (created by T1) with the schema
   migration policy section, the v1 -> v2 placeholder example from spec
   Section 5.2, and a callout that operators rebuild via `kanon install
   --refresh-lock`.
7. **Verify:** `uv run pytest tests/unit/test_lockfile_schema_migration.py -v`,
   then the full suite.

#### Critical Rules (Violation = Automatic Rejection)

1. **NO FALLBACK LOGIC** -- If an operation can fail, it MUST fail loudly. Never catch an exception and silently continue. Never provide a default value when the real value is missing. Exceptions: the resolver's documented lockfile-catalog-source fallback for `kanon install` / `kanon doctor`, and the existing `git ls-remote` retry policy (`KANON_GIT_RETRY_COUNT` / `KANON_GIT_RETRY_DELAY`) -- both in `spec/kanon-list-add-lock-features-spec.md` Section 4 header and Section 7.
2. **NO SILENT FAILURES** -- Every error must produce a clear, actionable error message sent to stderr. Every error must result in a non-zero exit code. Never swallow exceptions. Never log-and-continue when the operation was required to succeed.
3. **FAIL FAST** -- Detect errors at the earliest possible point. Validate inputs before processing. Check prerequisites before starting work. Exit immediately on the first error with a message that tells the user exactly what went wrong and what to do about it.
4. **NO HARD-CODED VALUES** -- No URLs, paths, timeouts, retry counts, port numbers, hostnames, credentials, feature flags, or environment-specific values in source code. All constants live in `src/kanon_cli/constants.py`, never inline in source files. All configuration comes from environment variables, configuration files, or function parameters.
5. **NO TEMPORAL LOGIC** -- Never use `time.sleep()`, `asyncio.sleep()`, or any time-based delay as a synchronization mechanism. The existing `KANON_GIT_RETRY_DELAY` (wait between known-failed `git ls-remote` retries) is the ONLY allowed sleep-based wait in this codebase. Use readiness detection, event-driven callbacks, or polling with configurable timeouts everywhere else.
6. **ALL CODE MUST BE DYNAMIC AND INPUT-DRIVEN** -- No static data, no hard-coded test fixtures embedded in source, no magic numbers. All thresholds, limits, paths, and identifiers must be parameterized.
7. **NO BYPASS ANNOTATIONS** -- Never add `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`, or any annotation that suppresses a linter, type checker, or security scanner finding. Fix the finding instead. The kanon repo has a documented vendored carve-out for `src/kanon_cli/repo/` (the embedded repo-tool fork): mypy and bandit scope to non-vendored code only. This carve-out is a scope demarcation, NOT a bypass annotation; do not extend it to new paths.
8. **NO DASH-EMS IN CODE OR TESTS** -- Do not use the em-dash character (Unicode U+2014) in any source file, test file, or work-unit `.md` file. Use `--` (double hyphen) in comments and docstrings if a dash is needed. `devbench validate-backlog` rule 10 enforces this on work-unit files.
