# E3: Lockfile + `kanon install` extension

## Status: in-queue

## Description

Epic for the `.kanon.lock` lockfile format and the `kanon install` lockfile
state machine. After this epic ships, `kanon install` behaves as follows:

- `.kanon` plus `.kanon.lock` is the single source of truth for what gets
  installed; the lockfile pins every transitive `<project>` to an immutable
  resolved SHA along with the manifest-source and `<include>` chain that
  produced it.
- The install command branches on a five-row state matrix (Section 4.7):
  lockfile absent, lockfile present and consistent (`kanon_hash` matches),
  lockfile present and stale (hash mismatch), lockfile references an
  unreachable SHA, lockfile records a different catalog source than the
  CLI/env source.
- Operators rebuild a stale lockfile with `--refresh-lock` (whole lockfile)
  or `--refresh-lock-source <name>` (one top-level source's chain).
- `--strict-lock` upgrades orphan-lock-entry warnings to hard errors;
  `--strict-drift` upgrades branch-drift notices to hard errors.
- The lockfile is TOML, schema-versioned, with a documented v1 schema and a
  per-version upgrade contract (Section 5.2).
- `<include>` cycles are detected via DFS and reported as `A.xml -> B.xml ->
  A.xml`; diamond `<include>` paths are deduped by canonical path.
- Two `<project>` entries that canonicalize (via `canonicalize_repo_url`) to
  the same repo URL but different SHAs are a hard conflict; the error names
  both source paths plus the canonicalization output.
- `<remote>` URLs in resolved manifests must be HTTPS or SSH; HTTP and
  `file://` require `KANON_ALLOW_INSECURE_REMOTES=1`.
- The lockfile path defaults to `<kanon-file-path>.lock` (so a non-default
  `--kanon-file` derives a sibling lockfile path) but `--lock-file` and
  `KANON_LOCK_FILE` always win.
- Today's `fcntl.flock` install-lock is extended to also cover `kanon add`,
  `kanon remove`, and `kanon doctor --refresh-completion-cache` so concurrent
  mutations of `.kanon` and the cache serialize correctly.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Sections 5, 5.1,
5.2, 4.7, 4.7.1, and 7.5 (concurrency extension).

E3 depends on E1 (widened PEP 440 resolution, `canonicalize_repo_url`, shared
`--catalog-source` CLI args module) and E2 (`derive_source_name` for the
`--refresh-lock-source <name|entry-name>` accept set, and `kanon add` /
`kanon remove` lock extension). E4 (`kanon outdated` / `kanon why`), E5
(`kanon doctor` workspace checks), E6 (`kanon catalog audit` consumer-side
checks), and E7 (documentation rollups) consume the lockfile schema and the
install state machine.
