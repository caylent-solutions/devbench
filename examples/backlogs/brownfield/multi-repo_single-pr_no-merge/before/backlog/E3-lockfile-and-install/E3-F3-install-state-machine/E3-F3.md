# E3-F3: `kanon install` lockfile state machine

## Status: in-queue

## Description

Extends `core/install.py::install` (today's resolver + symlink-aggregator)
with the lockfile state machine, the four new install flags, conflict
detection, `<include>` cycle / diamond handling, default `--lock-file`
derivation, HTTPS enforcement for resolved `<remote>` URLs, and the
extension of today's `fcntl.flock` concurrency lock to also cover
`kanon add` / `kanon remove` / `kanon doctor --refresh-completion-cache`.

The feature is broken into nine tasks; each task is narrowly scoped to one
row of the spec's state matrix or one flag, so the LLM judges can review
each in isolation and the orchestrator can parallelise non-overlapping
work where the DAG allows.

T1 lands the core state-matrix branching (the foundation every other task
depends on). T2 and T3 add the two `--refresh-lock*` flags. T4 adds the
two strictness flags. T5 wires `canonicalize_repo_url` into the conflict
detector. T6 implements `<include>` cycle / diamond handling. T7 derives
the default `--lock-file` path from `--kanon-file` (and accepts the
`KANON_LOCK_FILE` env override). T8 enforces HTTPS / SSH for `<remote>`
URLs in resolved manifests. T9 extracts today's install-only concurrency
lock into a reusable context manager and wires it into `add`, `remove`,
and the completion-cache refresher.

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 4.7 (state
matrix, flags, default-lockfile derivation, atomicity), Section 4.7.1
(install engine contract), Section 7.5 (concurrency lock extension), and
Section 3.6 (trust model / HTTPS).
