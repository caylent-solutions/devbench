# E10: Caylent-private-kanon engineering -- docs + CI guards

## Status: in-queue

## Description

This epic delivers the engineering scope (spec Section 9a) for the
`caylent/caylent-private-kanon` repo: documentation that codifies the
catalog-entry contract (the soft-spot 1-5 rules from spec Section 3.5) and
CI workflows that enforce that contract on every PR and push.

Two features:

- **E10-F1 -- Docs.** Update `README.md` to document the contract every
  catalog entry must satisfy (soft-spot 1-5). Create or update
  `docs/contributing.md` describing how to add a new catalog entry: a new
  `*-marketplace.xml` with a complete `<catalog-metadata>` block; NO
  per-entry directory. PEP 440 tag-publishing convention documented.
  Remove every doc passage describing `catalog/<name>/` as the
  entry-author surface.
- **E10-F2 -- CI guards.** New GitHub Actions workflows that run on every
  PR + push to main:
  1. `kanon catalog audit .` against the repo root (initially without
     `--strict`; promoted to `--strict` after the Phase 2 migration in
     E12 completes the deprecation window).
  2. `kanon validate xml`, `kanon validate marketplace`, AND `kanon
     validate metadata` (the new sub-subcommand from E5-F3).
  3. Smoke test: install latest kanon CLI, run `kanon list
     --catalog-source <this-repo-at-HEAD>`, assert returned entries
     match `git ls-files repo-specs/**/*-marketplace.xml`.
  4. Guard against new `catalog/<name>/` directories: `git diff
     --name-only origin/main..HEAD` must not introduce any path matching
     `^catalog/[^/]+/`.
  5. Guard against non-PEP 440 tag names: on tag push or PR-with-tag,
     validate the last path component is a valid PEP 440 version (warns
     initially per spec Section 9a / Section 15; future release promotes
     to hard error).

Spec source: `spec/kanon-list-add-lock-features-spec.md` Section 9a
(Engineering subsection: Docs + CI bullets 1-5). Operational migration
(Section 9b -- per-entry `<catalog-metadata>` migration + Phase 2
`catalog/` deletion) is tracked in a separate epic (E12); E10 ships the
docs and guards that codify and enforce the contract.

Upstream dependencies:

- **E5 -- `kanon doctor` + `kanon catalog audit` + `kanon validate
  metadata` + standards codification.** All E10 CI jobs invoke commands
  that ship in E5; the docs in E10-F1 reference the soft-spot 1-5 rules
  that E5-F2 codifies. The CI workflow cannot run before `kanon catalog
  audit` and `kanon validate metadata` exist upstream.
